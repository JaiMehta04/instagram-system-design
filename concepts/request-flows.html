TL;DR
  • Every Instagram feature is a chain of components. This lesson follows nine real user actions hop by hop, from the phone to storage and back, naming every box on the architecture diagram.
  • Almost every flow has two parts. A short synchronous part, where the user waits (target: a few hundred ms), and a longer asynchronous part that runs after the response through Kafka (fan-out, transcoding, indexing, notifications, analytics).
  • The API path (small JSON through Load Balancer → API Gateway → services) and the media path (large bytes going straight to Object Storage on upload and coming from the CDN on download) are always kept separate.
  • Reads are fast because the work was done ahead of time. Feeds are pre-computed by fan-out, renditions are pre-generated, and search is pre-indexed. Writes are fast because the expensive work is deferred to background workers.
  • Each flow below has an ASCII sequence diagram, numbered steps, a latency budget, a failure analysis and links to the lesson behind each concept. The lesson ends with a sync-vs-async summary table.

1. The problem: why trace requests end to end?

The other lessons teach one building block at a time: DNS, load balancing, caching, sharding, Kafka and so on. Real systems are never one block, though. When you double-tap a photo, at least six components take part in under a tenth of a second, and a few more keep working for seconds afterwards. Until you can trace that path, you don't really understand the system. Interviewers know this, so "walk me through what happens when…" is one of the most common system design questions.

Tracing a request end to end teaches you three things no single lesson can:

  • Where the time goes. A 200 ms budget gets split between network round trips, the gateway, cache lookups, database queries and ranking. If you know the budget, you know what to optimise.
  • What the user waits for and what they don't. The design trick behind Instagram's snappy feel is to make the user wait only for the minimum: "your post is saved". Everything else (resizing, fan-out to 500 followers, search indexing, push notifications) happens asynchronously.
  • What breaks, and what the user sees when it does. Every hop can fail. A good design decides, for each hop, whether to retry, fall back, degrade or fail loudly.
🧠 Analogy Think of sending a parcel. At the counter (the synchronous part) the clerk weighs it, takes payment and hands you a tracking number. You leave after two minutes. Sorting, trucks, planes and the final delivery van (the asynchronous part) take two days, and you don't stand at the counter waiting for them. If the clerk made you wait until the parcel arrived, the queue would reach around the block. Instagram's "201 Created" is the tracking number. Kafka is the sorting centre. The notification is the "delivered" text message.

2.1 Conventions used in every flow

  • DNS and the TLS connection are set up once. Flow 1 shows DNS resolution and the TLS handshake in full. After that the app reuses one long-lived HTTP/2 or HTTP/3 connection, so later flows skip those hops.
  • "LB + API Gateway" stands for two hops. The Load Balancer spreads connections over healthy gateway nodes. The API Gateway terminates TLS, validates the JWT (authentication), applies rate limits and routes to the right service. They are merged into one column to keep the diagrams readable.
  • Service-to-service calls inside the data center are gRPC or Thrift over persistent connections, with deadlines (see API design and microservices). Every call carries a trace ID so the whole flow shows up as one distributed trace.
  • "Post Meta (Cassandra)" is the diagram's Post/Comment/Story Metadata (Cassandra) store, partitioned by user_id or post_id (see sharding).
  • Arrow styles in the ASCII diagrams: -----> synchronous call, .....> response, ~~~~> asynchronous event via Kafka, -- local work inside one component.
  • All numbers are assumptions for a typical user on a good 4G/5G connection with ~40 ms round-trip time (RTT) to the nearest region. They are not official Instagram measurements.

2.2 The two golden rules behind every flow

⚡ Do the minimum synchronously

The synchronous path writes the source of truth (one row, one edge, one message), publishes an event, and returns. Everything that can be eventually consistent is pushed to Kafka consumers.

📦 Bytes never go through services

Uploads go straight to Object Storage with a pre-signed URL. Downloads come from the CDN. The API only ever carries IDs, metadata and URLs, so app servers stay small, stateless and cheap.

🧮 Precompute for reads

Instagram is read-heavy (assume ~100 reads per write). Feeds, story trays, renditions, counters and search indexes are built at write time so that reads are a few key lookups.

🔁 Make every step retry-safe

Networks fail and Kafka redelivers. Every write uses an idempotency key or a natural primary key, so doing it twice has the same effect as doing it once (see resilience patterns).

  1. Clients → DNS: the app resolves i.instagram.com. The phone's OS cache or the ISP's recursive resolver usually already has the answer. If not, the query reaches the authoritative DNS, which uses GeoDNS to pick a nearby, healthy region.
  2. DNS → Clients: returns the virtual IP (VIP) of that region's Load Balancer, with a short TTL (e.g. 60 s) so traffic can be moved quickly during an outage (see multi-region).
  3. Clients → Load Balancer: the app opens a TCP connection, performs a TLS 1.3 handshake (1 RTT, or 0 RTT on resumption; see networking basics) and sends POST /v1/auth/login {username, password, device_id}.
  4. Load Balancer → API Gateway: an L4 load balancer forwards the connection to a healthy gateway node, chosen by consistent hashing or least-connections. Health checks keep failed nodes out of rotation.
  5. API Gateway: terminates TLS. Login is one of the few unauthenticated routes, so instead of checking a token the gateway applies a strict rate limit per IP and per username (e.g. 5 attempts/min) to block credential stuffing.
  6. API Gateway → User/Auth Service: forwards the request as an internal gRPC call with a deadline (e.g. 1 s).
  7. User/Auth Service → User DB (PostgreSQL): looks up the account. Usernames map to a user_id through a lookup table. The user_id tells the service which shard holds the row, and reads can go to a read replica.
  8. User DB → User/Auth Service: returns user_id, the salted password hash, the account status and the 2FA settings.
  9. User/Auth Service (local): verifies the password with a deliberately slow hash (argon2 or bcrypt, ~50–100 ms of CPU) and runs risk checks (new device? impossible travel?). Risky logins get a 2FA or e-mail challenge instead of tokens. See authentication and security.
  10. User/Auth Service → User DB: writes a session record: the device and a hash of a new refresh token. This write goes to the shard's primary.
  11. User/Auth Service → Kafka: publishes user.logged_in asynchronously. Analytics & ML Training uses it for fraud models, and the Notification Service can send "new login from Chrome on Windows" alerts.
  12. User/Auth Service → API Gateway: returns a short-lived signed access token (a JWT, valid ~15–60 min) and a long-lived opaque refresh token (valid for weeks).
  13. API Gateway → Clients: 200 OK. The app stores the tokens in the iOS Keychain or Android Keystore. It then fires three calls in parallel over the same connection: the home feed (Flow 3), the stories tray (Flow 6) and POST /v1/devices {push_token}, which registers the APNs/FCM token used in Flow 9.

3.1 Every later app open (already logged in)

Login happens rarely. A normal cold start is much cheaper. The app paints the last feed it cached on disk immediately (see clients), reuses its tokens, and refreshes in the background. The gateway validates the JWT locally: it checks the signature with the Auth service's public key (cached), the expiry and the audience. No call to the User/Auth Service is needed, which takes the Auth service off the hot path of every request. If the access token has expired, the app calls POST /v1/auth/refresh once. The Auth service checks the refresh token against the User DB (where it can also be revoked) and issues a new JWT.

3.3 What happens on failure

  • DNS outage or slow resolver: the app keeps using cached IPs. Many large apps also ship fallback IPs or use multiple resolvers. A GeoDNS failover moves users to another region within roughly a TTL.
  • A gateway node dies: LB health checks drop it within seconds. Clients on that node reconnect, and the login is retried safely because nothing was committed.
  • User/Auth Service is down: new logins fail, but every existing session keeps working because JWTs are validated at the gateway without calling Auth. That containment is the main reason for using signed tokens. Refreshes fail too, so a long Auth outage slowly logs people out as access tokens expire.
  • User DB primary fails: credential reads still succeed from replicas, but session writes fail until a replica is promoted (seconds to tens of seconds; see replication). The gateway returns a retryable 503 and the app retries with exponential backoff plus jitter.
  • Brute-force attack: rate limits return 429 Too Many Requests. Repeated failures trigger CAPTCHA or account lockout.

4. Flow 2 — Uploading a photo post

This is the most important write in Instagram, and it touches the most components. The design goal is to make the user wait only until the photo is durably stored and the post row exists. Everything else (renditions, moderation, delivery into 500 followers' feeds, hashtag indexing, notifications) happens in the background. The flow has three phases.

The upload's critical path is the three green and yellow boxes. Everything purple runs after the user has been told "posted", in parallel, through Kafka consumers.

  1. Clients (local): the app applies filters, resizes the image to at most 1080 px wide and compresses it (a 12 MP camera photo of ~4 MB becomes ~300–600 KB). It also computes a content hash and generates an idempotency key (a random UUID) for this post. Doing this on the phone saves upload time and server CPU (see clients).
  2. Clients → LB + API Gateway: POST /v1/media/uploads {type: "image/jpeg", size, sha256} with the JWT.
  3. API Gateway → Upload Service: the JWT is valid and the upload rate limit is fine (e.g. 100 posts/day), so the request is routed.
  4. Upload Service (local): generates a globally unique, time-sortable media_id (see ID generation) and signs a pre-signed PUT URL for raw/{media_id} in Object Storage, valid for ~15 minutes and only for that key, content type and size. See media upload.
  5. Upload Service → Post/Comment/Story Metadata (Cassandra): records an upload session with status = PENDING, so abandoned uploads can be found and cleaned up later.
  6. Upload Service → Clients: returns {media_id, upload_url}. This hop is ~60 ms end to end.
  7. Clients → Object Storage: the app PUTs the bytes directly to Object Storage, bypassing the Load Balancer, API Gateway and Upload Service entirely. Large files (Reels) use multipart or resumable chunks of ~5–8 MB, so a dropped connection resumes from the last chunk instead of starting over.
  8. Object Storage → Clients: 200 OK with an ETag (checksum). The object is now durably stored, replicated or erasure-coded across devices and zones.
  9. Clients → LB + API Gateway: POST /v1/posts {media_id, caption, location, user_tags} with the header Idempotency-Key: 7c9e….
  10. API Gateway → Upload Service: routed. If the Upload Service has already seen this key (because the client retried after a timeout), it returns the original response instead of creating a second post. See API design.
  11. Upload Service → Object Storage: a HEAD raw/{media_id} confirms the object exists and its size and hash match, so a client cannot create a post pointing at nothing.
  12. Upload Service → Post/Comment/Story Metadata (Cassandra): inserts the post (post_id, user_id, media_key, caption, status = PROCESSING, created_at) into posts_by_id and posts_by_user. The post count on the profile is incremented in Feed Cache (Redis) counters.
  13. Upload Service → Kafka: publishes post.created {post_id, user_id, media_key, created_at}, keyed by user_id so that all of one user's events land in order on one partition (see Kafka). To guarantee the event is never lost when the DB write succeeds, use the transactional outbox pattern: write the event to an outbox table in the same write, and a relay publishes it.
  14. Upload Service → Clients: 201 Created {post_id}. The app already shows the post on the user's profile from the local file. The user is done.

4.5 What happens on failure

  • The network drops mid-upload: resumable/multipart upload continues from the last acknowledged chunk. If the pre-signed URL expires, the app asks for a new one with the same media_id.
  • The client times out on "create post" and retries: the idempotency key makes the retry return the same post_id, so there is no duplicate post.
  • Kafka is unavailable: with the outbox pattern the post row and the pending event are committed together, and a relay publishes it when Kafka recovers. Followers see the post late but never miss it. Without an outbox you get "posted but never appeared in feeds", a classic dual-write bug.
  • A media worker crashes halfway: it never committed its Kafka offset, so another worker gets the same event (at-least-once delivery). Renditions are written to deterministic keys, so redoing the work simply overwrites identical files. The operation is idempotent.
  • A poison message (e.g. a corrupt file that crashes the decoder) is retried a few times and then moved to a dead-letter queue; the post is marked FAILED and the user sees "Couldn't post, try again".
  • Fan-out lags behind (consumer lag during a spike): posting still succeeds. Followers' feeds are a little stale, autoscaling adds workers, and Flow 3's read path can pull very recent posts directly to fill the gap.

5. Flow 3 — Loading the home feed

This is the most frequent request in the system (assume ~5 billion feed loads a day, around 60k requests per second on average and 150k at peak). The goal is a p99 under ~300 ms server time. That is only possible because most of the work, deciding which posts are candidates, was done at write time in Flow 2.

  1. Clients (local): the app immediately renders the feed it saved on disk last time, so the user sees content in under 100 ms even on a bad network. It then asks the server for fresh content (stale-while-revalidate; see clients).
  2. Clients → LB + API Gateway: GET /v1/feed?cursor=<opaque>&limit=20 with the JWT. The cursor encodes where the previous page ended (cursor pagination, never offsets).
  3. API Gateway → News Feed Service: the JWT signature and expiry are verified locally, the user is under the rate limit, and the request is routed to any News Feed Service instance. The service is stateless (see microservices).
  4. News Feed Service → Feed Cache (Redis): ZREVRANGE timeline:{uid} 0 499 returns up to 500 post IDs that the fan-out workers pushed into this user's timeline. It's a single in-memory read of ~1 ms. See caching.
  5. News Feed Service → Follow/Graph: "which celebrities does this user follow?" These are the accounts excluded from push fan-out. The answer is small, and cached per user. In parallel with step 4.
  6. News Feed Service → Post/Comment/Story Metadata (Cassandra): fetches the last ~48 h of posts from each followed celebrity (posts_by_user is partitioned by author and clustered by time, so each fetch is one partition read; celebrities' recent posts are also heavily cached). This is the pull half of the hybrid model. See news feed.
  7. News Feed Service (local): merges the pushed and pulled candidates, removes posts that are deleted, blocked, muted or already seen, then ranks. A cheap first-stage model trims ~500 candidates to ~100, then a heavier model scores those using features like your affinity with the author, the post's early engagement and media type. It also inserts a few suggested posts. See analytics & ML ranking.
  8. News Feed Service → Feed Cache (Redis): hydrates the top 20. A multi-get fetches cached post objects (author, caption, rendition keys) and the like/comment counters.
  9. News Feed Service → Post/Comment/Story Metadata (Cassandra): fills any cache misses and writes them back to the cache (cache-aside).
  10. News Feed Service → Clients: JSON with 20 posts, each containing signed CDN URLs for several rendition sizes (never the bytes), plus next_cursor. Typical size ~30–60 KB, gzip/brotli compressed.
  11. Clients → CDN: the app picks the rendition for its screen and format support and fetches images in parallel. It prefetches the next few posts' media and the next page while the user scrolls.
  12. CDN → Clients: served from edge RAM/SSD on a hit (~10–30 ms). On a miss the edge goes through the origin shield to Object Storage. See CDN.
  13. Clients → Kafka (via the gateway): the app batches impression and view-time events and sends them every few seconds. They flow into Analytics & ML Training, which records what was seen (so it isn't shown again) and produces training labels for the ranking model.
Ranking is the largest single server-side cost; the network and CDN dominate what the user feels. The timeline read and the celebrity pull run in parallel, so the slower of the two counts.

5.2 What happens on failure

  • Timeline missing from Redis (new user, evicted inactive user, or a lost cache node): fall back to fan-out-on-read. Fetch the user's followees from the Social Graph store, read each one's recent posts from Cassandra, merge, then write the result back into Redis. This is slower (hundreds of ms) but correct, and it only happens once.
  • The ranking service is slow or down: after its deadline (say 80 ms) the News Feed Service degrades gracefully to a simple reverse-chronological order of the candidates. A slightly worse feed beats an error screen. See resilience patterns.
  • Some Cassandra replicas are slow: hedged requests or a lower consistency level (e.g. ONE) keep reads fast. Posts that can't be hydrated in time are dropped from this page rather than blocking it.
  • A cache node holding a celebrity's post gets hot: replicate hot keys across nodes or keep a small in-process cache in each News Feed Service instance (see caching on hot keys).
  • The whole feed backend is unavailable: the app keeps showing its cached feed with a "Couldn't refresh feed" banner and retries with backoff. A circuit breaker at the gateway stops retries from overwhelming a recovering service.
  • CDN edge miss storm or PoP failure: the origin shield collapses requests. Anycast or DNS moves users to the next PoP. Images load more slowly but still load.

6.2 What happens on failure

  • The request fails or times out: the app retries in the background with exponential backoff. Because the operation is idempotent, a retry after a "lost" success does no harm. If it finally gives up, the heart quietly turns back to grey.
  • Double-tap, like, unlike, like in one second: the client debounces and sends only the final state. The server applies requests in order per user, and each request carries a client timestamp so a stale "unlike" can't overwrite a newer "like".
  • Redis counter node lost: counts are approximate anyway. They can be rebuilt from the durable Cassandra totals plus a replay of recent like.created events. Users may briefly see a count that's slightly off, which is an acceptable eventual-consistency trade (see consistency models).
  • Viral post hot partition: the likes_by_post partition for one post can grow to tens of millions of rows. Bucket it as (post_id, bucket) so no single Cassandra partition grows unbounded (see sharding on hot spots).
  • Notification Service lagging: likes still succeed. Notifications arrive late, which nobody notices.

7.1 What happens on failure

  • Forward edge written, reverse edge write fails: the graph is now inconsistent: Alice "follows" Bob, but Bob's follower list doesn't include her, so she won't receive his posts. Fixes, from simplest to most robust: (a) retry the second write with backoff; (b) write only the forward edge synchronously and let a Kafka consumer of follow.created write the reverse edge idempotently, which gives at-least-once delivery and eventual consistency; (c) run a periodic repair job that compares the two indexes. A saga mindset ("every step has a retry or a compensation") is the right frame.
  • Double tap or retries: edge writes are upserts keyed on (follower, followee), so they're idempotent. Counters are only incremented when the edge was actually new.
  • Backfill lags: Alice doesn't see Bob's old posts for a few seconds. That's harmless.
  • Follow/unfollow spam bots: rate limits at the gateway and abuse models in Analytics & ML Training throttle or block them (see security).

9.2 What happens on failure

  • Elasticsearch slow or a shard down: a query fans out to all shards, so it's as slow as the slowest one. The Search Service sets a tight timeout and returns partial results from the shards that answered. The user rarely notices a slightly incomplete suggestion list.

11.1 What happens on failure

  • Notification Service is down: events accumulate in Kafka (retention of days), and nothing is lost. On recovery, stale notifications (e.g. likes older than an hour) are skipped rather than sent late; the Activity feed is still backfilled.
  • APNs/FCM outage: a circuit breaker stops hammering the provider, messages wait in a retry queue, and the in-app Activity feed still shows everything.
  • Duplicate events (at-least-once Kafka): a dedupe key per (recipient, event_id) in Redis with a TTL prevents double pushes.
  • Notification storm (a celebrity's post tagging 1M users, or a bug): per-user rate caps and global rate limiting on the sender protect both users and provider quotas.

13. How Instagram uses these patterns

📸 In Instagram Public engineering talks and blog posts describe how Instagram's request flows evolved. It started as a Python/Django application tier talking to sharded PostgreSQL, with IDs generated inside PostgreSQL using a 64-bit time + shard + sequence scheme (see ID generation). Later it added Cassandra for high-write data such as feeds, activity and direct messages, Memcache/Redis caches, and async task queues for fan-out and media work. After joining Facebook, it moved onto Meta's data centers, edge network and shared infrastructure. The exact internals are private, but the shape described in this lesson matches what has been made public: a thin synchronous path, direct-to-storage media, a CDN for bytes, precomputed feeds with special handling for celebrity accounts, and heavy use of asynchronous pipelines for everything else.

Three cross-cutting patterns run through all nine flows:

  1. Event-carried state. Every write publishes a domain event (post.created, like.created, follow.created…). New features (a new notification type, a new ML signal, a new index) are added as new consumers without touching the write path. That is the main architectural payoff of Kafka.
  2. Optimistic clients plus idempotent servers. The app assumes success (heart turns red, post appears, "Following" shows) and retries in the background. That is only safe because every server operation is idempotent: idempotency keys for posts, natural primary keys for likes and follows, client_msg_id for DMs.
  3. Graceful degradation per feature. Each service has a fallback: feed → chronological or cached, search → recents, tray → cached, push → Activity feed. A failure in one feature doesn't take down the app. These are bulkheads in practice.
📸 Rough end-to-end numbers (assumptions) With 500M daily active users: ~60k feed requests/s on average (~150k peak), ~60k likes/s, ~1.2k photo uploads/s, ~100k typeahead requests/s at peak, tens of millions of concurrent WebSocket connections for DMs, and media egress around 1 Tbps from the CDN. Notice that the async side multiplies these numbers: one upload by an account with 1,000 followers creates 1,000 timeline writes, so fan-out workers perform over a million Redis writes per second. See capacity estimation.

14. Trade-offs & common pitfalls

✅ Benefits of the "thin sync, fat async" shape

  • Low, predictable user-facing latency regardless of follower counts or video length
  • Failures in background work don't fail the user's request
  • Natural load levelling: Kafka absorbs spikes and workers drain at their own pace
  • Easy extensibility: add consumers without changing producers
  • Media path scales independently through Object Storage and the CDN

⚠️ Costs

  • Eventual consistency everywhere: followers, counts, search and notifications lag
  • Harder debugging: one user action becomes ~10 asynchronous hops (needs tracing)
  • Duplicate delivery means every consumer must be idempotent
  • Dual-write risk between DB and Kafka (needs an outbox or CDC)
  • Operational weight: Kafka, worker fleets, DLQs, lag monitoring

Common pitfalls when describing flows

  • Sending media through the API servers. It ties up app servers on slow uploads and wastes bandwidth twice. Always use pre-signed URLs and the CDN.
  • Doing fan-out synchronously in the post request. A user with 2M followers would wait minutes. Fan-out belongs in workers, and celebrities belong on the pull path.
  • Forgetting the failure path. For each hop, say what happens if it's slow or down: retry, fallback, degrade, or fail.
  • Treating push notifications as reliable delivery. They're hints. Durable stores plus client sync are the guarantee.
  • Ignoring idempotency. Mobile networks guarantee retries, so without idempotency keys you get duplicate posts and double-counted likes.
  • Publishing the event before (or without) committing the DB write. Consumers then act on data that doesn't exist. Commit first; use an outbox.
  • Calling the Auth service on every request. Validate signed tokens at the gateway instead.
  • Unbounded timeouts. Each hop needs a deadline smaller than its caller's, or one slow dependency cascades into a site-wide outage.

16. Interview corner

Walk me through what happens, end to end, when a user posts a photo.

The client resizes and compresses the photo, then asks the Upload Service (through the LB and API Gateway, which authenticate and rate-limit) for an upload slot. The service generates a time-sortable media ID and a pre-signed URL. The client PUTs the bytes directly to Object Storage, then calls POST /posts with an idempotency key. The Upload Service verifies the object exists, writes the post row to Cassandra (status PROCESSING), publishes post.created to Kafka (via an outbox), and returns 201. The user is done after ~100 ms of server work plus upload time. Asynchronously, media workers create renditions and run moderation, mark the post READY and emit post.ready. Fan-out workers then push the post ID into each follower's Redis timeline (skipping celebrities, who are pulled at read time), the Search Indexer indexes hashtags, the Notification Service handles mentions, and analytics records the event. Followers fetch the images from the CDN, which origin-pulls from Object Storage.

Why does the client upload directly to object storage instead of through the Upload Service?

Bytes through app servers would cost bandwidth twice, hold an app-server thread or connection for the full (possibly minutes-long) upload, and make the stateless tier scale with media volume instead of request count. A pre-signed URL keeps authorisation in our hands (it's scoped to one key, size and content type, and it expires) while Object Storage handles durability, multipart and resumable transfer at practically unlimited scale. The API path stays small and fast.

A user follows 2,000 accounts, including 15 celebrities. How is their feed served within 200 ms?

Most of the work happened at write time. Normal accounts' posts were already pushed into the user's Redis timeline by fan-out workers, so one sorted-set read returns ~500 candidate IDs. Celebrities were excluded from push fan-out, so in parallel the service reads the recent posts of those 15 accounts. These are 15 partition reads, heavily cached because millions of users need the same data. It merges, filters and ranks (two-stage, with a deadline and a chronological fallback), hydrates the top 20 from the post-object cache, and returns JSON with CDN URLs. The server-side p50 is ~85 ms; images then come from the nearest CDN edge.

How do you make sure a like isn't counted twice when the client retries?

Store likes keyed by (post_id, user_id), so a repeat is an upsert of the same row, and only increment the counter when the like is new: check the insert result, or use a Redis set-add that returns whether the member was new. The client uses PUT semantics ("I like this"), and the server orders a user's like/unlike operations by client timestamp. Kafka consumers downstream (notifications, analytics) dedupe on an event ID. Counters on hot posts are sharded and periodically reconciled against the durable count, because display counts may be approximate but must converge.

How does DM delivery differ when the recipient is offline?

In both cases the message is first durably written to the Messages Store with a per-thread sequence number and acked to the sender. If the presence registry shows a live connection, the server pushes it over the recipient's WebSocket. If not, it publishes an event that the Notification Service turns into an APNs/FCM push. Push is only a wake-up hint. When the recipient opens the app, it reconnects and asks for "all messages in thread X after seq N", which pulls the gap from the store. This makes delivery correct even if pushes are lost or duplicated, and the client dedupes by client_msg_id/seq.

What happens if Kafka is down when a post is created?

With a naive dual write ("write DB, then publish"), you'd get posts that exist but are never fanned out, indexed or processed. Instead use the transactional outbox: the post row and an outbox record are committed together, and a relay (or CDC from the commit log) publishes outbox records when Kafka is reachable, retrying until acknowledged. The user's request succeeds. Followers see the post late, but they never miss it. Consumers must be idempotent because the relay may publish twice.

Which parts of these flows need strong consistency and which can be eventual?

Strong (or at least read-your-writes): authentication and sessions, the author seeing their own new post, the per-thread order of DMs, privacy and block checks (showing a blocked user's content is a real harm), and payments if any. Eventual: follower feeds, like/view counters, search index, notifications, stories tray, analytics. The rule of thumb is to ask "what's the cost of the user seeing stale data for a few seconds?" For most social features it's negligible, and accepting it buys latency and availability (CAP/PACELC).

How would you find out why feed loads became slow last night?

Start from the SLO dashboard (p99 latency per endpoint and region) to locate when and where. Then use distributed traces: each feed request has spans for the gateway, timeline read, celebrity pull, ranking and hydration, so you can see which span grew. Correlate with deploys, cache hit ratio, Redis and Cassandra latency, ranking model version, and Kafka consumer lag (a lagging fan-out pushes more work onto the read path). Logs with the trace ID give details for individual slow requests. See observability.

17. Check your understanding

In Flow 2, which steps must succeed before the user sees "posted"? Which can fail without the user's request failing?

Must succeed: the upload slot (pre-signed URL), the PUT to Object Storage, the post row insert and the durable recording of the event (outbox). Can fail without failing the request, because they're retried asynchronously: renditions, moderation, fan-out, search indexing, notifications and analytics. If moderation later rejects the post, it's removed after the fact.

An account with 50,000 followers posts. Fan-out workers write to Redis with pipelines of 1,000 commands, ~2 ms per pipeline. Roughly how long does push fan-out take for one worker, and why is that acceptable?

50,000 / 1,000 = 50 pipelines × 2 ms ≈ 100 ms, plus paging through the follower list. It runs asynchronously, so nobody waits on it, and followers see the post within about a second. For a 50M-follower account it would be ~100 s of work per post and 50M writes, which is why such accounts use pull instead.

Why does the stories tray store author IDs rather than story IDs?

The tray shows one avatar per author. Storing authors means an author posting 10 stories updates each follower's tray once instead of 10 times (10× less fan-out). Individual story items are fetched from the per-author partition only for the authors actually displayed, and expired items disappear automatically via TTL.

The ranking service starts timing out. What does the user see, and why?

A feed in roughly reverse-chronological order (slightly less relevant), not an error. The News Feed Service calls ranking with a deadline and degrades gracefully to a simple ordering of the candidates it already has. Combined with a circuit breaker, this protects the user experience and gives the ranking service room to recover.

Typeahead: a user types "selena" in 600 ms. Without debouncing, how many requests are sent, and with a 100 ms debounce, roughly how many?

Without debouncing, 6 (one per keystroke). With a 100 ms debounce and keystrokes ~100 ms apart, typically 1–3, usually just the final "selena" plus perhaps an intermediate prefix. Across hundreds of millions of users that cuts typeahead QPS by 2–5×, and the prefix cache absorbs most of the rest.

Bob's phone was off for 6 hours and APNs dropped several notifications. Does Bob lose any DMs? Explain.

No. Messages were durably stored in the Messages Store before being acked to the sender. On reconnect, Bob's app syncs each thread from its last known sequence number and receives everything it missed, in order. Push notifications are only a hint to wake the user; they're not the delivery mechanism.

Which component(s) would you check first if new posts appear on the author's profile but not in followers' feeds?

The asynchronous path between the write and the timelines. Is post.created being published (outbox relay healthy)? Are media workers marking posts READY and emitting post.ready? What is the Kafka consumer lag for the Feed Fan-out Workers, and are any messages piling up in the dead-letter queue? Are the Redis timeline writes succeeding? The author's profile reads Cassandra directly, which is why it looks fine.

🎯 Key takeaways
  • Every flow is thin synchronous + fat asynchronous: write the source of truth, publish an event, return. Kafka consumers do the rest.
  • API path and media path are separate. Uploads go client → Object Storage via pre-signed URLs; downloads go CDN → client.
  • Reads are cheap because writes did the work: precomputed timelines (hybrid push/pull), renditions, counters and indexes.
  • Optimistic clients require idempotent servers: idempotency keys, natural primary keys and dedupe in consumers.
  • Know each flow's latency budget and each hop's failure behaviour (retry, fallback, degrade). That is what interviewers probe.
  • Push notifications are hints. Durable stores plus client sync are the delivery guarantee.
