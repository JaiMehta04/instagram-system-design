TL;DR
  • Chat flips the normal web model: the server must push messages to phones the instant they arrive. That needs a persistent connection per online device — usually a WebSocket (or MQTT, which Facebook Messenger publicly adopted) — instead of request/response polling.
  • Dedicated gateway servers each hold hundreds of thousands of open connections; a session registry (Redis: user → device → gateway) tells the stateless Chat Service where to route each message.
  • Messages are persisted before delivery in a wide-column store (Cassandra/HBase) partitioned by conversation_id and clustered by a time-ordered message ID; a per-conversation sequence number gives every participant the same order.
  • Delivery is at-least-once with acks and retries, made safe by client-generated message IDs for dedup. Offline devices get a push notification and sync from a cursor when they reconnect — which also keeps multiple devices in sync.
  • Receipts (sent ✓ / delivered ✓✓ / seen), presence (heartbeats) and typing indicators (ephemeral, best-effort) are separate, cheaper channels. E2EE (Signal protocol) means the server only relays ciphertext.

1. The problem: why is messaging different from everything else?

Almost everything else in Instagram is client-initiated: the app asks ("give me my feed", "like this post") and the server answers. Direct messages break that model. When your friend sends you "are you coming?", nobody on your side asked for it — the server has to reach your phone on its own, within a fraction of a second, while you're looking at a chat screen.

That single difference creates a cascade of hard problems:

  • Server push: plain HTTP can't push. We need a long-lived connection from every online device — that's tens or hundreds of millions of open connections at once.
  • Routing: the message arrives at one server; the recipient is connected to a different one, among hundreds. Who knows where they are?
  • Reliability: phones drop off networks constantly (elevators, tunnels, app backgrounded). A message must never be lost, never be shown twice, and must reach the user eventually even if they're offline for a week.
  • Ordering: if Alice sends "Do you want pizza?" then "Or sushi?", Bob must see them in that order — on every one of his devices, and in group chats everyone must see the same order.
  • State signals: delivered/seen receipts, "online now", "typing…" — all of which are high-frequency and must be cheap.
🧠 Analogy Think of a huge hotel switchboard. Every guest who's in their room has a phone line kept open to the front desk (the persistent connection). The desk has many operators (gateway servers), each handling thousands of lines, and a room directory on the wall saying which operator holds which guest's line (the session registry). When a message comes in for room 512, the desk first writes it in the logbook (persistence), checks the directory, and the right operator reads it down the open line. If the guest is out, the message stays in the logbook, a note is slipped under their door (push notification), and when they return they ask "anything since my last message, number 41?" (sync from a cursor).

2. Requirements and numbers

2.1 Functional requirements

  • 1:1 and group conversations (groups up to a few hundred members — an assumption).
  • Real-time delivery to online recipients; offline delivery when they return, plus push notifications.
  • Ordering: all participants see a conversation's messages in the same order.
  • Receipts: sent, delivered and read ("Seen").
  • Presence ("Active now", "Active 5m ago") and typing indicators.
  • Media: photos, videos, voice notes, shared posts/Reels.
  • Multi-device sync: phone, tablet and web show the same history and read state.
  • History: scroll back through old messages; inbox list sorted by last activity.
  • Optional: end-to-end encryption (E2EE).

2.2 Non-functional requirements

  • Low latency: end-to-end delivery to an online recipient in ~100–500 ms.
  • Durability: once the sender sees "sent", the message must never be lost.
  • Exactly-once appearance: no visible duplicates, even though the network forces retries.
  • High availability: chat is expected to "always work"; a gateway crash should cost a reconnect, not data.
  • Consistency: per-conversation ordering is required; global ordering across conversations is not.

2.3 Back-of-the-envelope (assumptions)

Assume 300M daily DM users, 40 messages sent per user per day
  → 12B messages/day → 12B / 86,400 ≈ 140,000 msgs/s average, ~400,000/s peak
  → deliveries are higher: a message to a 10-person group = 9 deliveries

Storage: ~300 bytes per message row (text + IDs + metadata; media stored separately in S3)
  → 12B × 300 B ≈ 3.6 TB/day ≈ 1.3 PB/year, ×3 replicas ≈ 4 PB/year

Concurrent connections at peak: assume ~150M online devices
  Each gateway server holds ~500k connections (tuned event-loop server)
  → 150M / 500k = 300 gateway servers (+ headroom for failures → ~400-500)

Heartbeats: 150M connections pinging every 30 s → 5M tiny frames/s
  (this is why heartbeats are handled at the gateway and never touch a database)

Notice the two very different workloads: a connection-holding tier (huge numbers of mostly idle sockets, low CPU) and a message-processing tier (hundreds of thousands of writes per second). Separating them is the first architectural decision.

3. Real-time transport: how can the server reach the phone?

HTTP is request/response: the client speaks first, the server answers, done. There are four classic ways to get "server push" anyway, plus MQTT.

  • Short polling at Instagram scale is absurd: 150M devices polling every 5 s = 30M requests/s, almost all answering "nothing new", and still up to 5 s of latency.
  • Long polling was the classic pre-WebSocket solution (early Facebook chat used it). It works through any proxy, but each delivered message costs a new HTTP request with full headers, and every hop must tolerate requests hanging for 30+ seconds.
  • SSE is great when only the server talks (live scores, a notification stream) and it auto-reconnects with a Last-Event-ID, but sending still needs separate HTTP requests.
  • WebSocket starts as an HTTP request with Upgrade: websocket; after a 101 Switching Protocols response the same TCP (+TLS) connection carries small bidirectional frames. This is the standard for browser chat and what our architecture diagram shows. See API design for how it fits next to REST and gRPC.
  • MQTT is a publish/subscribe protocol designed for unreliable, low-bandwidth networks. Facebook publicly wrote (2011) that Messenger used MQTT to keep a persistent connection with low battery and bandwidth cost; Meta's mobile apps have continued to use MQTT-based connections for real-time features. The concepts below are identical whichever protocol carries the bytes.
💡 Push notifications are not a transport APNs/FCM push notifications wake the app or show a banner when it's not connected; they're best-effort, rate-limited and may be delayed or collapsed. They complement the persistent connection for offline devices — they never replace it (see Notifications).

4. Gateway servers: holding millions of connections

A gateway (also called connection server, edge server or "front-end") is a server whose main job is to keep sockets open and shuttle frames between devices and the backend. It contains no business logic, which keeps it simple, stable and rarely redeployed.

Gateways hold connections; the stateless Chat Service persists, looks up where the recipient is connected, and routes the message to that gateway.

4.1 How one server holds 500,000+ connections

  • Event-driven I/O: instead of one thread per connection (500k threads would need hundreds of GB of stack memory and drown in context switches), the server uses an event loop on top of epoll (Linux) / kqueue: a few threads are told by the kernel "these 30 sockets have data", handle them, and go back to waiting. Netty (Java), Go's netpoller, Node.js, Erlang/BEAM all work this way. WhatsApp publicly reported holding over 2 million connections on a single Erlang server back in 2012.
  • Memory per connection is the real limit: kernel socket buffers + TLS session state + application state ≈ 10–50 KB each. 500k × 30 KB ≈ 15 GB of RAM — fine for a modern server.
  • OS tuning: raise the file-descriptor limit (each socket is a file descriptor), tune TCP buffer sizes and keep-alive. A server listening on one port can hold millions of connections (each is identified by the client's IP and port, so the server's ports don't run out).
  • TLS termination at the gateway (or a TLS-terminating L4 proxy in front of it), using session resumption so reconnects are cheap (see Networking basics).

4.2 Load balancing long-lived connections

A load balancer spreads new connections across gateways (least-connections works well). But connections live for hours, so the usual "add servers and traffic rebalances" doesn't happen by itself:

  • Deploys and draining: to restart a gateway, stop routing new connections to it, then close existing ones gradually (e.g. over 10 minutes) with a "please reconnect" frame so clients move to other gateways.
  • Reconnect storms: if a gateway with 500k connections crashes, 500k clients reconnect at once — and each reconnect triggers a TLS handshake, an auth check and a sync. Clients must use exponential backoff with random jitter (e.g. retry after random 0–2 s, then 0–4 s…), and the backend must rate-limit sync work (see Resilience patterns).
  • Heartbeats (ping/pong every ~30–60 s) keep NATs and mobile carrier middleboxes from silently dropping idle connections and let the gateway detect dead clients.

5. The session registry: who is connected where?

When Alice's message for Bob arrives, the Chat Service must know: is Bob online, on which devices, and which gateway holds each device's connection? That mapping is the session registry, typically a Redis cluster (fast, in-memory, with TTLs).

# Bob's phone connects to gateway 47 (connection id c-88123)
HSET   sess:bob  phone-7f3a  "gw47|c-88123|1730000000"
EXPIRE sess:bob  90                    # refreshed by every heartbeat; auto-expires if gateway dies

# Bob's laptop connects to gateway 12
HSET   sess:bob  web-21cc    "gw12|c-55102|1730000004"

# Chat Service routing a message to Bob
HGETALL sess:bob
→ phone-7f3a: gw47|c-88123|…   web-21cc: gw12|c-55102|…   → deliver to BOTH gateways

# Clean disconnect
HDEL   sess:bob  phone-7f3a
  • Per device, not per user: each device has its own connection and its own sync cursor (multi-device).
  • TTL as a safety net: if a gateway crashes without cleaning up, entries expire within ~90 s. Until then a route may point at a dead gateway — delivery fails, and the message is simply picked up on reconnect via sync. The registry is a hint, never the source of truth for delivery.
  • Load: writes happen on connect/disconnect (and TTL refresh, which can be batched per gateway), reads once per message recipient. Both are cheap single-key operations, sharded across a Redis cluster by user ID.
  • Gateway-to-gateway routing: once you know "gw47", how do you send to it? Either a direct RPC (Chat Service → gw47's internal address), or a pub/sub channel per gateway (Redis pub/sub or a lightweight broker topic gw47 that the gateway subscribes to). Direct RPC is simplest and lowest latency.

Important details hidden in those steps:

  • Persist before ack (step 6 → 7): Alice's "sent ✓" means the message is durably stored (written to a quorum of replicas). If the Chat Service crashes after step 6 but before step 7, Alice's app retries with the same client_msg_id and step 4 recognises the duplicate.
  • Persist before deliver: Bob may receive it via real-time push or via sync later — both read from the same stored log, so nothing depends on the push succeeding.
  • Delivery is decoupled from sending: steps 9–12 can fail (Bob's gateway just died) without affecting Alice. The message waits in storage; Bob's next sync fetches it.
  • Sender's other devices: Alice's laptop must also show the message she sent from her phone — so the Chat Service delivers it to all of Alice's other devices too (multi-device sync is "deliver to everyone in the conversation, including the sender's other devices").
  • Offline path: if step 9 finds no sessions for Bob, the Kafka event at step 8 lets the Notification Service send a push notification (step 9 may also explicitly trigger it).
  • Media messages: the app first uploads the photo/voice note to object storage with a pre-signed URL, then sends a normal message containing the media key. Recipients download via the CDN with signed URLs. Chat servers never relay large binary payloads.

7. Storing messages

7.1 Access patterns decide the model

Chat storage is overwhelmingly write-heavy and read in one specific way: "the latest N messages of conversation X, then the N before that as I scroll up", plus "everything in X after sequence S" for sync. Messages are almost never updated (except edits, unsends and reactions). That's a perfect fit for a wide-column store (see Databases) built on LSM-trees, which turns random writes into sequential ones (see Indexing).

-- Cassandra-style schema (CQL)
CREATE TABLE messages (
  conversation_id  bigint,
  bucket           int,        -- e.g. month number: bounds partition size
  message_id       bigint,     -- 64-bit time-ordered ID (Snowflake/Instagram-style)
  seq              bigint,     -- per-conversation sequence number
  sender_id        bigint,
  client_msg_id    uuid,       -- sender-generated idempotency key
  type             text,       -- text | media | post_share | reaction | system
  body             blob,       -- text, or ciphertext if E2EE
  media_ref        text,
  PRIMARY KEY ((conversation_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

-- "Load the chat": newest 30 messages
SELECT * FROM messages WHERE conversation_id = 9 AND bucket = 658 LIMIT 30;
-- "Scroll up": 30 older than the oldest I have
SELECT * FROM messages WHERE conversation_id = 9 AND bucket = 658
  AND message_id < 7234011234567890 LIMIT 30;
  • Partition key = conversation_id (plus a time bucket): all messages of a conversation live together on the same replica set, so reading a chat is a single-partition, sequential read. Different conversations spread evenly across the cluster (sharding by hash of the partition key — consistent hashing in Cassandra).
  • Clustering key = message_id descending: within a partition rows are physically sorted, so "latest 30" is the first 30 rows — no sorting at query time. A time-ordered 64-bit ID (timestamp in the high bits, see ID generation) gives roughly chronological order and uniqueness without coordination.
  • Buckets prevent unbounded partitions: a group chat active for five years could accumulate millions of messages; Cassandra partitions should stay well under ~100 MB. Bucketing by month means "scroll up" occasionally crosses into the previous bucket.

7.2 The inbox (conversation list)

The DM inbox shows your conversations sorted by latest activity with a preview and unread badge. That's a different access pattern ("all conversations for user U, newest first"), so it gets its own table, maintained asynchronously from the Kafka message events:

user_inbox: PRIMARY KEY (user_id, last_activity_ts DESC, conversation_id)
            → last message preview, unread count, muted flag
conversation_members: PRIMARY KEY (conversation_id, user_id) → role, joined_at, read/delivered watermarks

Because Cassandra can't "update the sort key in place", moving a conversation to the top means delete-old-row + insert-new-row; many systems instead keep the inbox in Redis sorted sets (score = last activity) backed by the durable table.

8. Ordering: everyone sees the same sequence

8.1 Why timestamps alone fail

  • Client clocks lie. A phone with a clock 3 minutes fast would place its messages "in the future". Never order by device time.
  • Server clocks drift too. Two Chat Service instances receiving Alice's and Bob's simultaneous messages may disagree by a few milliseconds; time-ordered IDs from different machines aren't strictly ordered across machines (see ID generation).
  • Concurrent sends in a group chat: if Carol and Dan send at the same moment, both orders are "correct" — what matters is that everyone sees the same one.

8.2 Per-conversation sequence numbers

The robust solution is a monotonic sequence number per conversation: 1, 2, 3, … assigned by the server at write time. It gives a total order within a conversation (which is all users can perceive) while different conversations proceed fully in parallel — no global ordering bottleneck.

Who assigns seq without races?

ApproachHowTrade-off
Single writer per conversation ⭐Route all sends for conversation c9 to one owner (e.g. hash(conversation_id) → a Chat Service shard, or a Kafka partition keyed by conversation_id consumed by one worker). The owner increments an in-memory counter, persisted with each message.Simple, fast, strictly ordered. Needs failover: a new owner must read the last seq from storage before continuing.
Atomic counterINCR seq:c9 in Redis before writing the message.Easy, but the counter becomes a durability concern (lost on failover without persistence) and every message needs an extra round trip.
Conditional writeCompare-and-set / lightweight transaction: insert seq = last+1 only if it doesn't exist.Correct, but consensus-based writes (e.g. Cassandra LWT/Paxos) are several times slower.

On the client side:

  • The sender's message is shown immediately with a pending state at the bottom, then repositioned (if necessary) when the ACK returns its real seq.
  • Recipients insert messages by seq. If they receive seq 45 while their last is 43, they know 44 is missing (perhaps still in flight, perhaps lost on a dying connection) and request the gap via sync.
  • Sequence numbers double as sync cursors and receipt watermarks ("read up to 45") — one concept, three uses.

9. Delivery guarantees: at-least-once plus dedup

Networks offer no "exactly-once delivery". A send can fail in three indistinguishable ways: the request was lost, the server crashed after processing, or the ACK was lost. The client can't tell which — so it must retry, and retries create duplicates. The standard recipe (see delivery guarantees and idempotency keys):

  1. The client generates a unique client_msg_id (a UUID) when the user hits send, and stores the message in a local outbox.
  2. It sends and waits for an ACK; on timeout it retries with the same client_msg_id (with backoff), across reconnects and even app restarts.
  3. The server keeps a dedup record (sender, client_msg_id) → (msg_id, seq) for a period (e.g. 24 h in Redis, or a unique index in the store). A duplicate send simply returns the original ACK — idempotent.
  4. Server → recipient delivery is also at-least-once: the gateway pushes, waits for the device's ACK, and the backend relies on sync to fill anything un-acked. The recipient dedups by msg_id (a local unique index) before displaying.
// client-side outbox (simplified)
function send(convId, text) {
  const msg = { clientMsgId: uuidv4(), convId, text, state: "PENDING" };
  localDb.outbox.insert(msg);  ui.append(msg);
  trySend(msg);
}
function trySend(msg, attempt = 0) {
  socket.send({ type: "SEND", ...msg });
  timers.set(msg.clientMsgId, setTimeout(
    () => trySend(msg, attempt + 1),
    Math.min(30000, 1000 * 2 ** attempt) * (0.5 + Math.random())));  // backoff + jitter
}
socket.on("ACK", ({ clientMsgId, msgId, seq }) => {
  clearTimeout(timers.get(clientMsgId));
  localDb.outbox.markSent(clientMsgId, msgId, seq);    // ✓ sent
});

The combination — at-least-once transport + idempotent processing + dedup on display — gives users the experience of exactly-once, which is the only kind of exactly-once real distributed systems can offer.

10. Offline users, push and sync

Most of the time the recipient is not connected: the app is closed or the phone is asleep. The design must treat offline as the normal case.

  1. Store: the message is already durable in the messages store (step 6 above). Nothing is "queued for Bob" separately — the conversation log is the queue.
  2. Notify: the Notification Service, consuming the message event from Kafka, sends a push via APNs/FCM: "Alice: pizza?" (or a generic "New message" when content must stay private). Pushes for the same conversation are collapsed so 20 messages don't produce 20 banners.
  3. Reconnect: when Bob opens the app, it establishes a connection, registers in the session registry, and immediately syncs.
  4. Sync from a cursor: the device sends the last position it has fully processed; the server returns everything after it, in order, in pages.

Two common cursor designs:

11. Receipts: sent, delivered, seen

🕓 Pendingin local outbox
→server ACK
✓ Sentdurably stored
→device ACK
✓✓ Deliveredon recipient device
→chat opened
👁 Seenread watermark

A naive design stores a status row per message per recipient and updates it twice. For a 100-member group that's 200 writes per message — far more than the message itself. The efficient design uses watermarks:

  • For each (conversation, member) store last_delivered_seq and last_read_seq. Because sequence numbers are ordered, "read up to 45" implies 1–45 are all read. One small update covers any number of messages.
  • Bob's device sends read(c9, up_to=45) when the chat is visible; the server updates the watermark only if it increases (monotonic — duplicates and out-of-order receipts are harmless) and relays it to the other members' devices as an event.
  • The sender's UI computes each message's state by comparing its seq with the watermarks: in a group, "Seen by Carol, Dan + 3" = members whose last_read_seq ≥ seq.
  • Receipts are coalesced: if Bob reads 30 messages, one receipt is sent, not 30. Delivered receipts can be batched per device every second or so.
  • Users can disable read receipts; the server then simply doesn't relay them (it may still store the watermark to sync Bob's own devices' unread badges).

12. Presence and typing indicators

12.1 Presence via heartbeats

Presence = is the user online now, or when were they last active? The gateway already knows when a connection opens, closes or goes silent, so presence is derived from connection state plus heartbeats:

# on connect and on every heartbeat (~30 s), the gateway batches updates:
SET presence:bob  "online"  EX 70          # expires if 2 heartbeats are missed
SET last_active:bob 1730000123             # for "Active 5m ago"

# a viewer's inbox shows 20 conversations → one batched read:
MGET presence:alice presence:carol presence:dan ...
  • Don't broadcast every change to everyone. If each of 150M users toggles online/offline ~10 times a day and has ~200 contacts, pushing every change would be 300B presence messages/day. Instead use interest-based delivery: fetch presence when you open the inbox or a chat (pull), and subscribe to live changes only for the conversations currently on screen.
  • Debounce flapping: a phone switching from Wi-Fi to 4G disconnects for a second. Mark someone offline only after the TTL expires (e.g. ~60 s without heartbeat), and treat a quick reconnect as continuous presence.
  • Approximate is fine: "Active now" being 30 s stale is invisible to users, so presence lives only in memory with TTLs — never in the durable store.
  • Privacy: users can hide activity status; presence is only shown to people you follow or have chatted with.

12.2 Typing indicators

"Alice is typing…" is the most ephemeral signal of all:

  • The client sends typing(c9) when the user starts typing and then at most once every ~3–5 s while they keep typing — never per keystroke.
  • The Chat Service relays it straight to the online participants' gateways: no persistence, no Kafka, no retries, no push notifications, no sync. If it's lost, nobody cares.
  • The receiver shows the indicator and auto-hides it after ~5–6 s without a refresh (so a sender who closes the app doesn't leave "typing…" forever).
  • Under load, typing indicators are the first thing to shed (see graceful degradation).
💡 Classify every signal by its guarantees Messages: durable, ordered, at-least-once, synced. Receipts: durable watermarks, monotonic, coalesced. Presence: in-memory, TTL'd, pulled on demand. Typing: fire-and-forget. Giving each signal only the guarantees it needs is what keeps the system affordable.

13. Group conversations and fan-out

A message to a group of n members needs n − 1 deliveries (times the number of devices each). The question — just like in the news feed — is where to fan out.

Shared conversation log (write once) ⭐Per-member copies (write diffusion)
Storage write1 row in messages for the conversationn rows, one in each member's mailbox
Reading historyRead the conversation partitionRead your own mailbox
Per-member workSmall: inbox pointer/unread count + user update-log entry + delivery to online devicesFull message copy per member
Edits, unsend, reactionsChange one rowChange n rows
Best forGroups of any size; the defaultSmall groups where per-user mailboxes simplify sync (some systems do this)

Delivery itself always fans out: the Chat Service looks up the members (cached conversation_members), batch-reads their sessions from the registry (one pipelined call), groups the target devices by gateway, and sends one batched RPC per gateway containing all of its recipients. For a 250-member group with ~1.5 devices online each, that's ~370 device pushes but only a few dozen RPCs. Offline members get a (collapsed, possibly muted) push notification and pick the message up on sync.

  • Cap group size (a few hundred members) so fan-out per message stays bounded; very large audiences are a different product (broadcast channels) with fan-out-on-read semantics.
  • Ordering in groups comes from the same per-conversation seq — critical because concurrent senders are common.
  • Membership changes are themselves messages in the log ("Dan added Erin") with a seq, so every device applies them in the same order relative to messages; a removed member stops receiving deliveries from that seq onward.

14. End-to-end encryption (E2EE) basics

With normal (transport) encryption, TLS protects messages on the wire, but the server decrypts and stores them — so the company (or an attacker who breaches it) could read them. With end-to-end encryption, only the participants' devices hold the keys; the server stores and forwards ciphertext it cannot read.

14.1 The Signal protocol idea

The Signal protocol, used by Signal and WhatsApp and adopted by Meta for Messenger and Instagram DMs, combines two pieces:

  1. Key publication: each device generates a long-term identity key pair, a signed prekey and a batch of one-time prekeys, and uploads only the public halves to the server's key directory. Private keys never leave the device.
  2. X3DH (initial key agreement): to start a chat with Bob even while he's offline, Alice fetches Bob's public "prekey bundle" and combines several Diffie-Hellman calculations (her identity and a fresh ephemeral key with his identity, signed prekey and a one-time prekey). Both sides can derive the same shared secret, but the server — which only saw public keys — cannot.
  3. Double Ratchet (ongoing messages): every message is encrypted with a new key derived by "ratcheting" a chain forward, mixed with fresh Diffie-Hellman exchanges as replies flow. Stealing today's key doesn't decrypt past messages (forward secrecy), and the conversation heals after a compromise once new DH exchanges happen (post-compromise security).
 Bob's device                    Server (relay + key directory)                 Alice's device
 gen IK_B, SPK_B, OPK_B[1..100]
 ── upload PUBLIC keys ─────────► stores IK_B, SPK_B, OPK_B…
                                 ◄──────────────────── fetch Bob's bundle ───── (first message)
                                                         X3DH: DH(IK_A,SPK_B), DH(EK_A,IK_B),
                                                               DH(EK_A,SPK_B), DH(EK_A,OPK_B) → secret
                                 ◄─── ciphertext + EK_A(public) + OPK id ────── Double Ratchet: msg key #1

14.2 What E2EE changes in the system design

  • Multi-device: each device has its own keys, so the sender encrypts a message separately for every device of every participant (client-side fan-out). Groups use "sender keys": a sender distributes a group key once per member device (pairwise-encrypted), then encrypts each message once.
  • Server features shrink: no server-side search of message text, no server-generated link previews, no content-based spam/abuse scanning (systems rely on metadata, user reports — which forward the reported plaintext — and client-side signals instead).
  • History and new devices: a new device can't decrypt old messages from the server; history needs encrypted backups or device-to-device transfer.
  • Metadata remains visible: who talks to whom and when is still needed for routing; minimising and protecting it is a separate effort (see Security & privacy).
  • The storage, ordering, receipts and sync designs above are unchanged — they just carry opaque body bytes.

16. How Instagram uses real-time messaging

  1. When the app is open, it keeps a persistent connection through the load balancer to a gateway (the diagram's "Direct Messaging (WebSocket)" service).
  2. Sending a DM goes over that connection to the Direct Messaging service, which validates, sequences and persists it in the Messages Store (Cassandra/HBase), then routes it via the session registry to the recipient's gateway.
  3. A Kafka event drives the inbox update, analytics, and the Notification Service → APNs/FCM push for offline recipients.
  4. Photos, videos and voice notes go to Object Storage via pre-signed URLs and are served by the CDN; shared posts and Reels are sent as references (IDs), hydrated like feed posts.
  5. On reconnect, the app syncs from its cursor, so the phone, tablet and web client converge on the same history and read state.
📸 In Instagram Instagram Direct launched in 2013. In 2020 Meta publicly announced cross-app messaging between Instagram and Messenger, which implies the two share messaging infrastructure. Facebook's public engineering posts describe Messenger's evolution: MQTT persistent connections on mobile (2011), HBase message storage (2010), a per-user ordered sync queue called Iris (2014), a move of storage to MySQL/MyRocks (2018), and Signal-protocol-based E2EE rolled out for Messenger and Instagram DMs. Exact internals and numbers are not public; the design in this lesson is consistent with those public descriptions and with how other large chat systems (WhatsApp, Discord, Slack) describe theirs.

17. Trade-offs & common pitfalls

✅ Persistent connections + durable log + sync: benefits

  • Sub-second delivery to online users
  • No message loss: persist-before-ack, sync fills every gap
  • No visible duplicates thanks to client IDs and dedup
  • Same order on every device via per-conversation seq
  • Multi-device and offline handled by one mechanism (cursor sync)
  • Gateways are simple and stable; logic lives in stateless services

⚠️ Costs

  • Hundreds of stateful gateway servers and reconnect-storm risk
  • Session registry is a soft-state dependency that can be stale
  • Per-conversation sequencing needs single-writer routing and failover care
  • Receipts and presence can generate more traffic than messages
  • E2EE removes server-side search, previews and content moderation
  • Multi-region conversations add latency and complexity

Common pitfalls

  • Acking before persisting — a crash loses messages the sender believes were sent.
  • Treating the push notification or the WebSocket push as the delivery guarantee — both are best-effort; the stored log + sync is the guarantee.
  • Ordering by client timestamps — clock skew scrambles conversations. Use server-assigned per-conversation sequence numbers.
  • Retrying without an idempotency key — duplicate messages on flaky networks.
  • Per-message receipt rows — use monotonic watermarks.
  • Broadcasting presence to all contacts — use pull + subscribe-while-visible.
  • Business logic in gateways — every logic change then forces reconnecting millions of clients.
  • Clients reconnecting without jitter — a gateway crash becomes a self-inflicted DDoS.
  • Unbounded partitions for long-lived busy conversations — bucket by time.

19. Interview corner

Design Instagram Direct. Walk me through sending a message.

Online devices keep a WebSocket/MQTT connection to a gateway; the gateway registers user/device → gateway in a Redis session registry. Alice sends {conversation_id, client_msg_id, body}; the gateway forwards to the stateless Chat Service, which authorises, dedups on client_msg_id, assigns a time-ordered msg_id and a per-conversation seq (single writer per conversation), writes to Cassandra (partition conversation_id+bucket, clustered by msg_id), then ACKs Alice ("sent"). It publishes a Kafka event (inbox, notifications, analytics), looks up Bob's devices in the registry and pushes to their gateways; Bob's device ACKs ("delivered") and later sends a read watermark ("seen"). If Bob is offline, he gets an APNs/FCM push and syncs from his cursor on reconnect.

WebSockets vs long polling vs SSE — which and why?

WebSockets (or MQTT on mobile): full-duplex, tiny frame overhead, real-time in both directions — exactly what chat with typing indicators and receipts needs. Long polling works through any proxy and is a good fallback, but costs a full HTTP request per delivery and hanging requests at every hop. SSE is server→client only, so sends need separate HTTP calls; good for notification streams, not interactive chat. Short polling wastes enormous capacity and still adds seconds of latency.

How do you guarantee messages are not lost and not duplicated?

No loss: persist to a replicated store before ACKing the sender; the client keeps unacked messages in a local outbox and retries; recipients get messages either by push or by cursor-based sync from the durable log, so a failed push is never a lost message. No duplicates: the client attaches a UUID client_msg_id reused across retries; the server dedups (sender, client_msg_id) and returns the original ACK; recipients dedup by msg_id before display. That's at-least-once delivery with idempotent processing — effectively exactly-once to the user.

How do you order messages in a group chat?

A per-conversation monotonically increasing sequence number assigned by a single writer for that conversation (route by hash of conversation_id to an owner; on failover the new owner reads the last seq from storage). Every member orders by seq, so everyone sees the same order; clients detect gaps (got 45, have 43) and fetch the missing range via sync. Client timestamps are never used for ordering; time-ordered IDs alone aren't strictly ordered across servers.

A gateway server with 400k connections crashes. What happens?

Those clients detect the broken connection (TCP reset or missed heartbeat) and reconnect with exponential backoff + jitter, landing on other gateways via the load balancer. Registry entries for the dead gateway expire via TTL (or are cleaned by a health monitor). Messages routed to the dead gateway in the meantime fail to deliver but are already persisted; each reconnecting client syncs from its cursor and receives them. Backend sync capacity must be rate-limited to absorb the burst; no data is lost.

How would you implement presence for hundreds of millions of users?

Derive it from connections: gateways batch heartbeat updates into Redis keys with TTL (~60–70 s) plus a last_active timestamp. Don't push presence changes to all contacts; clients fetch presence for visible conversations (batched MGET) and subscribe to changes only while a chat or inbox is on screen. Debounce flapping by waiting for TTL expiry before showing offline. Keep it in memory only; it's approximate by design and respects privacy settings.

Why Cassandra/HBase for messages, and what's the key design?

The workload is write-heavy, append-only, time-ordered, enormous, and read as "latest N of a conversation" or "everything after seq S" — ideal for an LSM-based wide-column store that scales horizontally with built-in replication. Partition key (conversation_id, time bucket) keeps a conversation together and bounds partition size; clustering key message_id DESC stores rows pre-sorted for newest-first reads. Facebook publicly used HBase for Messages. The inbox (per-user conversation list) is a separate table/sorted set because it's a different access pattern.

What changes if we add end-to-end encryption?

Devices generate key pairs and upload public prekeys; senders run X3DH to establish a shared secret and Double Ratchet to derive per-message keys (forward secrecy). The server stores and routes ciphertext only. Each device of each participant needs its own encrypted copy (or sender keys for groups), so client-side fan-out grows. We lose server-side message search, link previews and content scanning; history on new devices needs encrypted backup. Ordering, receipts, storage and sync stay the same — they operate on metadata.

20. Check your understanding

150M devices short-poll every 5 seconds. How many requests per second is that, and what fraction is wasted if a device receives a message on average once every 10 minutes?

150M / 5 = 30M requests/s. A device polls 120 times per 10 minutes and gets data in ~1 of them, so ~99% of requests return nothing — and messages still wait up to 5 s. This is why persistent connections are used.

Why does the Chat Service persist the message before sending the ACK to the sender, rather than after delivering to the recipient?

The ACK is a promise that the message won't be lost. Persisting first makes that true even if the service crashes immediately after. Waiting for delivery would make sending as slow as the recipient's network — and impossible when the recipient is offline. Delivery is a separate, retriable step backed by sync.

Bob's phone received messages with seq 41, 42 and 44 in conversation c9. What should it do?

Display 41 and 42; hold 44 (or display it with a gap) and request the missing range via sync (seq > 42). Seq 43 may still be in flight or may have been lost on a broken connection; the sync from the durable log guarantees it arrives, and then 43 and 44 are shown in order.

Alice taps send in a tunnel; the request reaches the server and is stored, but the ACK is lost. She retries 3 times. How many messages does Bob see, and why?

One. All retries carry the same client_msg_id; the server finds (alice, client_msg_id) already processed and returns the original msg_id/seq without storing a new row. Even if a duplicate delivery reached Bob, his app dedups by msg_id.

A group has 200 members and receives 1,000 messages a day. Compare receipt writes for per-message status rows vs watermarks if each member reads the chat 5 times a day.

Per-message rows: 1,000 messages × 199 recipients × 2 statuses ≈ ~400,000 writes/day. Watermarks: each member advances read (and delivered) watermarks a handful of times per session — e.g. 200 members × 5 reads × ~2 updates ≈ ~2,000 writes/day. Roughly 200× fewer.

Which of these should be persisted durably: (a) a message, (b) a typing indicator, (c) a read receipt, (d) "Active now"?

(a) yes — the source of truth. (c) yes, as a compact watermark, so read state syncs across devices. (b) no — fire-and-forget relay. (d) no — in-memory with a TTL; only the coarse last_active timestamp might be persisted.

Why should gateways contain no business logic?

Every gateway deploy disconnects hundreds of thousands of clients, causing reconnect storms and sync load. Keeping gateways as dumb connection holders means they rarely change, while logic (validation, sequencing, routing) lives in stateless services that can be redeployed freely without dropping connections.

With 500k connections per gateway at ~30 KB each, how much RAM does connection state need, and how many gateways for 150M connections with 30% headroom?

500k × 30 KB ≈ 15 GB per server. 150M / 500k = 300 servers; with 30% headroom (to absorb a failed server's or zone's reconnects) ≈ ~390–400 gateways.

🎯 Key takeaways
  • Chat needs server push: persistent WebSocket/MQTT connections held by dedicated, logic-free gateways (hundreds of thousands of sockets each via event loops).
  • A TTL'd session registry maps user → device → gateway so the stateless Chat Service can route; it's a hint, not a guarantee.
  • Persist before ACK in a store partitioned by conversation_id and clustered by time-ordered message ID; order by a server-assigned per-conversation seq.
  • At-least-once + client_msg_id dedup = no loss, no duplicates. Offline users get push notifications and cursor-based sync, which also powers multi-device.
  • Give each signal only the guarantees it needs: receipts as watermarks, presence via heartbeats + TTL, typing as fire-and-forget.
  • E2EE (Signal: X3DH + Double Ratchet) makes the server a relay of ciphertext — the pipeline stays, server-side content features go away.
