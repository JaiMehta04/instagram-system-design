TL;DR
  • A raw upload is not what users download. The media pipeline turns one original into many renditions: validated, privacy-scrubbed (EXIF/GPS removed), correctly rotated, resized, re-encoded (JPEG/WebP/AVIF), plus thumbnails and tiny blurred placeholders.
  • Videos are transcoded into a bitrate ladder (240p…1080p) with modern codecs (H.264, HEVC, VP9, AV1), cut into 2–6 s HLS/DASH segments, so players can do adaptive bitrate streaming.
  • Work is driven by Kafka events into autoscaled worker pools that execute a task DAG with retries, idempotent outputs, priorities and (for video) GPU/ASIC hardware encoders.
  • Content moderation runs in the pipeline: perceptual-hash matching (PhotoDNA, PDQ) against known illegal content, ML classifiers, and human review queues; ML also generates automatic alt text.
  • A post state machine (UPLOADED → PROCESSING → PUBLISHED, or FAILED/REJECTED) keeps it all consistent; lazy transcoding of rare renditions and spending expensive encodes only on popular videos keep costs sane.

1. The problem: why process media at all?

A modern phone produces a 12–48 megapixel photo of 2–6 MB (often in Apple's HEIC format) and 4K HDR video at 20–50 Mbit/s. Now think about who views it on Instagram: a user on a 5-year-old Android phone with a 720-pixel-wide screen on a congested 3G network in a rural area, a user on a new iPhone on Wi-Fi, and someone on a desktop browser that can't decode HEIC at all. Serving the original to all of them would be wrong in every way:

  • Too big: downloading 5 MB to display a 640-pixel-wide image wastes ~95% of the bytes, the user's data plan and our CDN bandwidth. Feeds would scroll at a crawl.
  • Incompatible: not every device decodes HEIC, HEVC, AV1 or HDR.
  • Unsafe for privacy: photos carry EXIF metadata including the exact GPS coordinates where they were taken — often the user's home.
  • Unsafe for the platform: uploads may be malformed (or deliberately malicious) files, or prohibited content that must never be published.
  • Not streamable: a single large video file can't adapt to a network that drops from 20 Mbit/s to 1 Mbit/s mid-playback.

So every upload goes through a media processing pipeline that produces a set of safe, optimised, device-appropriate renditions, stores them in object storage, and lets the CDN serve the right one to each viewer.

🧠 Analogy Think of a photo lab and print shop. A customer drops off a raw negative. Before anything is printed, a clerk checks it's really film (validation), removes the customer's address label stuck on the envelope (EXIF stripping), turns it the right way up (orientation), and an inspector checks nothing illegal is on it (moderation). Then the lab produces wallet, postcard and poster prints (renditions) on different paper types (formats), a contact sheet of thumbnails, and for a home movie, copies on different tape qualities so it plays on any player (bitrate ladder). Big orders are split among many technicians (worker pools), urgent orders jump the queue (priorities), and the order slip tracks status: received → in the lab → ready for pickup (state machine).

2. The pipeline at a glance

The media pipeline is a fan-out/fan-in DAG: sequential safety steps first, then parallel rendition, moderation and enrichment tasks, then a join that publishes the post.

The order matters: validate before decoding further (security), normalise before producing renditions (so every rendition is upright and metadata-free), run renditions and moderation in parallel, and only flip the post to PUBLISHED when the required outputs and checks are complete.

3. Image processing stages

3.1 Validation

  • Check the real type by magic bytes (FF D8 FF = JPEG, 89 50 4E 47 = PNG, ftypheic = HEIC), never the file extension or the client-supplied Content-Type.
  • Limits: max file size (e.g. 50 MB photo), max dimensions and total pixel count. A tiny 50 KB PNG can declare 50,000 × 50,000 pixels and expand to 10 GB in memory — a decompression bomb. Read the header first and reject before decoding.
  • Decode in a sandbox: image/video decoders are complex C code with a long history of vulnerabilities (e.g. the 2016 "ImageTragick" ImageMagick flaw allowed remote code execution via crafted images). Run workers with least privilege, seccomp/containers, no network access except storage, and a strict allow-list of formats.
  • Integrity: verify the uploaded size/checksum matches what the client declared; compute a content hash (for dedup and for moderation hash checks).
  • Video: probe with ffprobe: container, codecs, duration (Reels max length), resolution, frame rate, rotation, audio presence, corrupted streams.

3.2 EXIF stripping (privacy)

EXIF (Exchangeable Image File Format) metadata is embedded by cameras: camera make/model, lens, exposure, timestamps, sometimes the device serial number, a thumbnail of the original, and — critically — GPS latitude/longitude, accurate to a few metres. Publishing it would reveal where users live, where their children go to school, or where a vulnerable person is hiding.

$ exiftool IMG_4821.HEIC
Make                 : Apple
Model                : iPhone 15 Pro
Date/Time Original   : 2026:10:23 14:41:07
Orientation          : Rotate 90 CW
GPS Latitude         : 19 deg 4' 33.12" N        ← user's home, to ~3 m
GPS Longitude        : 72 deg 52' 40.56" E
Lens Model           : iPhone 15 Pro back triple camera 6.765mm f/1.78

The pipeline re-encodes every rendition from decoded pixels and writes no metadata except what's needed for correct display (e.g. an ICC colour profile). Anything useful (capture time, a location the user chose to tag) is stored as structured fields in the post's metadata DB, under the user's control — not hidden in the file. Re-encoding (rather than editing tags) also defeats metadata hidden in unusual places (XMP, IPTC, maker notes, trailing bytes after the image).

3.3 Orientation fix

Phone sensors capture in one fixed orientation. Instead of rotating pixels, the camera saves them as captured and sets the EXIF Orientation tag (values 1–8: normal, mirrored, rotated 90°/180°/270°, and mirrored+rotated). Viewers are supposed to apply it. If you strip EXIF without first applying the rotation, half your portrait photos show up sideways. So: read the Orientation tag, physically rotate/flip the pixels, then drop the tag. (Videos have a similar rotation flag in the container metadata.)

3.4 Resizing to multiple renditions

Generate a fixed set of widths covering common screen sizes and layouts — for example 1080, 750, 640, 480 and 320 px for the feed, plus small square crops (150–240 px) for profile grids and thumbnails. Instagram displays feed photos between 1.91:1 landscape and 4:5 portrait, 1080 px wide at most, so larger inputs are scaled down and out-of-range aspect ratios are cropped.

  • Resampling filter: high-quality downscaling uses filters such as Lanczos or Catmull-Rom; naive nearest-neighbour causes aliasing (jagged edges, moiré). Add mild sharpening after large reductions.
  • Resize from the best source once, or cascade (1080 → 640 → 320) for speed — fewer decode passes, slight quality cost.
  • Colour: convert wide-gamut (Display P3) and HDR inputs to sRGB/SDR for broad compatibility, or keep a P3-tagged variant for capable devices.
  • Fast libraries: libvips (streaming, low memory) is typically several times faster than ImageMagick for this workload; JPEG decoders can also decode at 1/2, 1/4 or 1/8 scale directly ("shrink-on-load"), a huge saving when making thumbnails.

3.6 Quality vs compression trade-offs

Lossy encoders expose a quality knob (JPEG/WebP "q" 0–100, AVIF quantizer/CRF). Higher quality → bigger files; beyond ~85 the extra bytes are mostly invisible. Practical techniques:

  • Pick quality per rendition: thumbnails tolerate lower quality (q≈70) than a full-screen 1080 px image (q≈80–85).
  • Chroma subsampling 4:2:0: store colour at half resolution (eyes are less sensitive to colour detail than brightness) — ~30–50% savings for little visible loss.
  • Perceptual targets instead of fixed q: measure quality with metrics such as SSIM, Butteraugli or VMAF and binary-search the lowest quality that meets a target score. A flat blue sky compresses far better than a forest, so per-image tuning can save another ~10–30%.

3.7 Thumbnails and placeholders (blurhash)

Even a 70 KB image takes a moment on a slow network. To avoid blank grey boxes while scrolling, the pipeline produces placeholders small enough to embed directly in the feed API's JSON, so they're shown instantly before any image request:

  • Dominant colour — a single hex colour (a few bytes).
  • BlurHash — the image is reduced to a handful of low-frequency colour components (a small grid of DCT-like coefficients, e.g. 4×3) and encoded as a ~20–30 character base83 string such as LEHV6nWB2yk8pyo0adR*.7kCMdnj. The client decodes it into a smooth, blurred gradient matching the photo's colours and layout, then cross-fades to the real image.
  • Tiny preview (LQIP) — a very low-resolution JPEG/WebP (e.g. ~40 px wide, a few hundred bytes) scaled up with a blur. Facebook publicly described sending ~200-byte preview photos inside API responses by stripping the standard JPEG header (which the app already knows) from tiny thumbnails.
  • Video poster frame / animated preview — a representative frame (chosen by a quality/face heuristic, not just frame 0) and short low-res preview clips for grids.

4. Video processing

4.1 Codecs vs containers

Two terms beginners often confuse:

  • A codec (coder/decoder) is the compression algorithm for the video (or audio) stream itself: H.264, HEVC, VP9, AV1 for video; AAC or Opus for audio.
  • A container is the file format that wraps one or more encoded streams plus timing and metadata: MP4 (and fragmented MP4 / CMAF), MOV, WebM, MPEG-TS. "An .mp4 file" says nothing certain about which codec is inside.

Video codecs exploit redundancy in space (within a frame, like JPEG) and in time (consecutive frames are similar). Frames come in three kinds: I-frames (keyframes — self-contained, large), P-frames (store differences from previous frames using motion vectors) and B-frames (reference both past and future frames — smallest). A GOP (group of pictures) runs from one keyframe to the next. A player can only start decoding — or switch quality — at a keyframe, so keyframes must be placed at every segment boundary, aligned across all renditions (e.g. a keyframe every 2 s with 4 s segments).

4.3 Segmenting: HLS and DASH

Each rendition is cut into short segments (typically 2–6 s) plus manifests that describe them:

  • HLS (HTTP Live Streaming, Apple): .m3u8 text playlists — a master playlist listing the variants and a media playlist per variant listing segments.
  • MPEG-DASH: an XML .mpd manifest describing "representations" and segment templates.
  • CMAF: a common fragmented-MP4 segment format both HLS and DASH can reference, so you store segments once and serve two manifests.

#EXT-X-STREAM-INF:BANDWIDTH=2128000,RESOLUTION=720x1280,CODECS="avc1.4d401f,mp4a.40.2"

Segments are small immutable files — perfect for CDN caching. Short-form apps also commonly use a single progressive MP4 per rendition fetched with HTTP Range requests for the very first seconds (fastest start), switching to ABR segments as playback continues.

4.4 Adaptive bitrate (ABR) playback

The player downloads the manifest, then fetches segments one at a time, choosing the rung for each segment based on measured throughput and how many seconds of video are buffered:

  • Throughput-based algorithms pick the highest rung below the recent measured bandwidth (with a safety margin).
  • Buffer-based algorithms (e.g. BOLA) pick rungs from buffer level: low buffer → low rung, full buffer → climb.
  • Fast start: begin with a low/medium rung (and prefetch the first segment of the next Reels in the feed) so playback starts in < 200 ms, then climb.
  • The goal is to minimise rebuffering (stalls hurt engagement far more than slightly lower resolution) while maximising quality and avoiding constant switching.

5. Orchestrating the pipeline

5.1 Kafka → worker pools → task DAG

When an upload completes, the Upload Service publishes media.uploaded to Kafka. A pipeline orchestrator consumes it and expands it into a DAG (directed acyclic graph) of tasks, each executed by a specialised worker pool:

A video DAG: probe, split into chunks at keyframes, encode every chunk of every rung in parallel, stitch and package into HLS/DASH, and publish only when the gate's required inputs (renditions + moderation verdict) are present.
  • Chunked parallel encoding: a 90 s Reel split into 10 s chunks (at keyframes) × 5 rungs = 45 independent encode tasks; with enough workers the wall-clock time approaches the time to encode a single chunk.
  • Separate pools per resource type: CPU pools for images, GPU/ASIC pools for video, GPU pools for ML moderation — each sized and autoscaled independently.
  • Workflow state (which tasks are done, outputs, attempts) lives in a database or a workflow engine (Temporal, AWS Step Functions, Netflix Conductor), not in worker memory, so any worker can resume a half-finished DAG.

5.2 Retries and idempotency

Workers crash, spot instances vanish, storage calls time out; Kafka delivers at least once. Every task must therefore be safe to run twice:

  • Deterministic output keys: the output location is a pure function of the input, e.g. {hash}/p/{media_id}/v1/720p/seg_003.m4s. Re-running overwrites the same object with identical content — harmless.
  • Check before work: if the output already exists (HEAD request) and the task is marked done, skip.
  • Conditional state updates: mark tasks done with compare-and-set (UPDATE … SET state='DONE' WHERE task_id=? AND state='RUNNING').
  • Retry policy: exponential backoff with jitter for transient errors; a max attempt count; permanent errors (corrupt file) fail fast; exhausted retries go to a dead-letter queue and the post to FAILED with a user-visible "upload failed, retry?" (see Resilience Patterns).
  • Timeouts / leases: a task claimed by a worker that dies is re-queued after its lease expires.

5.3 Priorities and autoscaling

  • Critical path first: to publish quickly, produce only what's needed for the first view — e.g. the 1080 + 640 px images, a thumbnail and placeholder, or the 360p/720p H.264 rungs for video — in a high-priority queue. The remaining rungs and advanced codecs follow in lower-priority queues after the post is live.
  • Separate lanes: interactive uploads vs bulk re-encoding/backfill jobs (e.g. re-encoding old photos to AVIF) never share a queue, so a backfill can't delay a user's post.
  • Autoscale on lag / queue age: uploads peak in the evening and around events (New Year); scale pools on consumer lag and oldest-task age rather than CPU alone. Low-priority batch work can soak up idle capacity and cheap spot instances off-peak.

5.4 GPU and hardware encoders

Software encoders (x264, x265, libvpx, SVT-AV1) give the best compression per bit at slow presets but cost lots of CPU. Hardware encoders — GPU blocks such as NVIDIA NVENC and Intel Quick Sync, or dedicated ASICs — encode many streams in real time at a fraction of the power, at somewhat lower compression efficiency than the slowest software presets. Large platforms build their own: Google described its Argos video coding unit for YouTube, and Meta announced the MSVP (Meta Scalable Video Processor) ASIC for transcoding video-on-demand and live streams. A common split: hardware for the fast, high-volume first encodes; high-effort software encodes for the most-watched content where every saved bit is multiplied by millions of views.

6. Content moderation in the pipeline

Instagram must keep illegal and policy-violating content off the platform at the scale of hundreds of millions of uploads per day. Moderation is layered, from cheap and certain to expensive and nuanced:

6.1 Perceptual hashing: known illegal content

A cryptographic hash (SHA-256) changes completely if a single pixel changes, so re-saving, resizing or cropping an image defeats it. A perceptual hash instead summarises what the image looks like: visually similar images get hashes that differ in only a few bits, measured by Hamming distance (the number of differing bits).

# dHash - the simplest perceptual hash, to build intuition (64 bits)
def dhash(img):
    g = img.convert("L").resize((9, 8))          # grayscale, 9×8 pixels: throws away detail & colour
    px = list(g.getdata())
    bits = 0
    for row in range(8):
        for col in range(8):                     # is each pixel brighter than its right neighbour?
            left, right = px[row * 9 + col], px[row * 9 + col + 1]
            bits = (bits << 1) | (left > right)
    return bits

def is_match(h1, h2, threshold=10):
    return bin(h1 ^ h2).count("1") <= threshold  # Hamming distance: few differing bits = same picture

Production hashes are far more robust: PhotoDNA (developed by Microsoft and Dartmouth, licensed to platforms and used industry-wide) and Meta's open-sourced PDQ (256-bit, for photos) and TMK+PDQF (for video). Platforms check every upload against hash lists of known child sexual abuse material (CSAM) maintained with organisations such as NCMEC, and against shared databases of known terrorist content (e.g. GIFCT's hash-sharing database). A match is a near-certain verdict: the upload is blocked before publishing, evidence is preserved for the legally required report (US providers must report apparent CSAM to NCMEC), and the account is actioned by specialised teams. Hash matching is cheap (compute a hash, look up nearby hashes in an index), so it runs synchronously on every upload, and lists are re-applied retroactively when new hashes are added.

6.2 ML classifiers: new content

Hashes only catch known items. For everything else, ML models score each image (and sampled video frames, audio transcripts and on-image text via OCR) for policy areas: nudity/sexual content, graphic violence, hate symbols, self-harm, spam/scams, and more. Each model outputs a probability, and thresholds map scores to actions:

Score bandActionWhy
Very high confidence violationBlock or remove automaticallyPrecision is high enough that waiting for a human only spreads harm
Uncertain / borderlinePublish with reduced distribution (e.g. not eligible for Explore/recommendations) and/or queue for human reviewAvoid wrongly removing legitimate posts; humans decide
LowAllowMost content

Thresholds are tuned per policy and per surface: missing CSAM is unacceptable, so recall is pushed very high and humans absorb the extra false positives; for lower-severity policies, precision matters more. Heavy models run on GPU pools in parallel with transcoding so they add little to time-to-publish; some run asynchronously after publishing, with takedown if they fire later.

6.3 Human review queues

  • Items flagged by models, by user reports or by proactive sweeps land in review queues, prioritised by severity and predicted reach (a borderline post going viral jumps ahead of one with 10 views).
  • Reviewers see the content with policy guidance; tools reduce harm to reviewers (blurring, greyscale, muted audio by default).
  • Decisions feed back as training labels for the classifiers and as new hashes so the same content is caught automatically next time.
  • Users can appeal; appeals go to a separate queue.

See Security & Privacy for abuse prevention more broadly.

7. Automatic alt text

Blind and low-vision users rely on screen readers (VoiceOver, TalkBack), which read an image's alt text. Most people never write one, so the pipeline generates it: object/scene-recognition or image-captioning models produce a description such as "Photo may contain: 2 people, smiling, beach, ocean, sunset". Facebook launched automatic alt text in 2016, and Instagram added automatic and custom alt text in 2018. The generated text is stored in the post's metadata (users can override it with their own), delivered in the API response, and — with privacy care — can be a signal for search and content understanding (see Search). It's an ML task that runs on the same GPU pool as moderation, off the critical path.

8. Cost optimisations

Media processing is one of the largest compute bills in a photo/video product, and its outputs drive storage and CDN bills. The big levers:

  • Lazy / on-demand renditions: eagerly produce only the common renditions. A rare one (an unusual size for a tablet layout, a new format) is generated on first request: CDN miss → origin image service → not in storage → generate from the original (or nearest larger rendition), store it, return it, with request coalescing so a burst produces it once. You trade a slower first request for never computing or storing renditions nobody asks for.
  • Spend expensive encodes only where they pay back: every video gets a cheap H.264 ladder; when a video's watch time crosses a threshold (or is predicted to), enqueue AV1/VP9/HEVC encodes. Views follow a power law, so a small fraction of videos carries most watch time. Meta engineers have publicly described this kind of prioritisation for Instagram video, producing basic encodings for everything and advanced encodings for content predicted to be watched most.
  • Client-side pre-processing: the app resizes (e.g. to 1080 px) and compresses before uploading — less upload time on mobile, less server CPU. Instagram has publicly talked about starting the upload in the background while the user is still writing the caption, so "Share" feels instant.
  • Deduplication: identical re-uploads (memes, reposts) detected by content hash reuse existing renditions.
  • Hardware encoders and spot capacity for high-volume and batch work; efficient libraries (libvips, shrink-on-load).
  • Storage hygiene: expire raw uploads; keep originals in cheaper tiers; drop renditions that can be regenerated (see Object Storage).
Is an AV1 encode worth it for one video? (all inputs are assumptions)
  AV1 encode cost: ~10 core-minutes ≈ 0.17 core-h × $0.03/core-h  ≈ $0.005

9. The post state machine

Many asynchronous steps must end in one consistent answer to "can people see this post?". A state machine stored with the post's metadata makes that explicit:

The post lifecycle. Only PUBLISHED posts are returned by feed, profile and search APIs; every transition is a conditional update so duplicate or late events can't move a post backwards.
  • Transitions are conditional (compare-and-set): UPDATE posts SET state='PUBLISHED' WHERE id=? AND state='PROCESSING'. A duplicate "processing done" event, or a late one for a post the user already deleted, changes nothing.
  • The publish gate fires when the required outputs exist and blocking checks have passed; non-critical outputs (extra rungs, AV1, alt text) may arrive after PUBLISHED.
  • Timeouts: a sweeper moves posts stuck in PROCESSING too long to retry or FAILED; UPLOADING posts whose upload URL expired become ABANDONED and their raw objects are cleaned up.
  • Side effects on entering PUBLISHED: emit post.created (via the outbox — see Message Queues) to trigger feed fan-out, search indexing and notifications. Fan-out must not happen earlier, or followers would see a post with missing media.
  • Optimistic UI: the author's app shows the post immediately from local data while the server is still processing; the client polls or receives a push when it's live (see Clients).

12. Trade-offs & common pitfalls

✅ What the pipeline buys

  • Fast loads and smooth playback on every device and network
  • Huge bandwidth savings (renditions + modern codecs)
  • Privacy (no GPS leaks) and security (malformed files rejected)
  • Platform safety via hashing, ML and human review
  • Accessibility via alt text

⚠️ What it costs

  • Large compute bill (video encoding dominates) and storage for many renditions
  • Time-to-publish latency and eventual consistency
  • Complex orchestration: DAGs, retries, partial failures
  • Codec support fragmentation across devices
  • Moderation errors either way: false positives anger users, false negatives cause harm

Common pitfalls

  • Stripping EXIF before applying orientation → sideways photos.
  • Forgetting metadata in other places (XMP, video container tags) → GPS leaks. Re-encode from pixels.
  • Decoding untrusted files unsandboxed or without pixel limits → RCE or decompression-bomb OOMs.
  • Misaligned keyframes across rungs → glitches or stalls when ABR switches.
  • Publishing before moderation/renditions are ready → broken images in followers' feeds or harmful content going live.
  • Non-idempotent tasks (random output names) → duplicates and orphaned objects on retry.
  • One queue for everything → a bulk re-encode backlog delays users' posts.
  • Encoding every video with the most expensive codec → compute cost explodes for videos nobody watches.

14. Interview corner

Design the photo processing pipeline for Instagram.

Client uploads directly to a raw bucket via a pre-signed URL; the Upload Service publishes media.uploaded and sets the post to PROCESSING. A worker pool consumes it: validate (magic bytes, size/pixel limits, sandboxed decode), apply EXIF orientation then strip all metadata, compute perceptual hashes and check against known-bad lists (block on match), produce renditions (e.g. 1080/640/320 px + thumbnails) in JPEG and WebP/AVIF with tuned quality, generate BlurHash and alt text, run classifiers. Outputs go to object storage under deterministic keys; a conditional state update to PUBLISHED triggers post.created for fan-out. Tasks are idempotent and retried with backoff; failures go to a DLQ and FAILED state. Pools autoscale on lag; critical renditions run in a high-priority lane.

How does adaptive bitrate streaming work and what does the backend have to produce?

The backend transcodes each video into a ladder of renditions (e.g. 240p–1080p at increasing bitrates), with keyframes aligned at fixed intervals, cuts each into 2–6 s segments, and writes HLS/DASH manifests listing variants and segments. The player downloads the manifest and then picks a rendition per segment based on measured throughput and buffer level, stepping down before the buffer empties and back up when bandwidth recovers. Segments are static files cached by the CDN.

Transcoding a 10-minute 4K video takes 20 minutes on one machine. How do you make it fast?

Split it at keyframes into chunks (say 10 s), encode every chunk of every rung in parallel across a worker pool (60 chunks × 5 rungs = 300 tasks), then stitch and package. Use hardware encoders for the first-available rungs, publish as soon as a playable subset (e.g. 360p/720p) is ready, and add higher rungs and advanced codecs later at lower priority. Ensure consistent encoder settings and closed GOPs so chunks join seamlessly.

How do you prevent known illegal images from ever being published?

Compute robust perceptual hashes (PhotoDNA, PDQ; TMK+PDQF for video) synchronously during processing, before the post can transition to PUBLISHED, and look them up against industry hash lists with a Hamming-distance threshold. A match blocks publication, preserves evidence, triggers the legally required report and account action through a specialised workflow. Re-scan existing content when new hashes arrive. ML classifiers and human review cover previously unseen content.

Video encoding costs are exploding. What do you do?

Encode a cheap baseline (H.264 ladder, possibly fewer rungs, hardware encoders) for every upload; reserve expensive codecs (AV1) and high-effort presets for videos predicted or observed to get high watch time, since views follow a power law; generate rare renditions lazily; use per-title encoding to avoid wasting bits on simple content; run batch work on spot capacity; dedupe re-uploads; and move to dedicated hardware encoders at scale. Measure with cost per watch-hour and quality metrics (VMAF), not just per-upload cost.

Why must the pipeline be idempotent, and how do you make it so?

Kafka delivers at least once and workers crash mid-task, so tasks will run more than once. Use deterministic output keys derived from (media_id, rendition, version), so re-running overwrites identical bytes; check for existing outputs before working; record task completion and post state with compare-and-set updates; and dedupe side effects (like emitting post.created) via the state transition — only the transition into PUBLISHED emits, and it can only happen once.

15. Check your understanding

Why does a portrait iPhone photo show sideways after a naive "strip all EXIF" step?

The phone stored the pixels in sensor orientation and recorded the needed rotation in the EXIF Orientation tag. Stripping the tag without first rotating the pixels loses that instruction. Fix: apply the orientation to the pixels, then strip.

What is the difference between a codec and a container? Give one example of each.

A codec compresses the media stream (H.264, AV1, AAC); a container packages encoded streams with timing/metadata into a file (MP4, WebM, MPEG-TS). The same MP4 container can hold H.264 or AV1 video.

A 720p rung is encoded at 2,000 kbps video + 128 kbps audio. How big is a 45 s clip?

2,128 kbps × 45 s = 95,760 kbit ≈ 95.8 Mbit ÷ 8 ≈ 12 MB.

Why must keyframes be aligned across all rungs of the ladder?

A player can only start decoding at a keyframe. ABR switches rendition at segment boundaries; if every rung has a keyframe at exactly the same timestamps (each segment starts with one), the player can switch cleanly. Misaligned keyframes cause glitches, stalls or the need to download overlapping data.

Two images: one is a re-saved, slightly cropped copy of the other. Will SHA-256 detect them as the same? Will PDQ?

SHA-256: no — any byte change produces a completely different hash. PDQ: likely yes — perceptual hashes of visually similar images differ in few bits, so the Hamming distance falls under the match threshold.

Using the break-even estimate in section 8, should you AV1-encode a Reel that will be watched ~40 times? ~10,000 times?

At ~160 views break-even: 40 views — no (encode cost exceeds bandwidth saved); 10,000 views — yes, savings are ~60× the encode cost, and viewers on slow networks get better quality.

A "media processed" event arrives twice for the same post; the user deleted the post in between. What should happen, and what mechanism guarantees it?

Nothing should change: the post must stay DELETED and no post.created should be emitted. A conditional state transition (… WHERE state = 'PROCESSING') fails for a DELETED post and for an already-PUBLISHED post, making the handler idempotent.

🎯 Key takeaways
  • Never serve the original: validate → strip EXIF (after fixing orientation) → resize → re-encode into multiple sizes and formats, plus thumbnails and BlurHash placeholders.
  • Video = codec inside a container, transcoded into a bitrate ladder, segmented for HLS/DASH, played with ABR; align keyframes.
  • Orchestrate with Kafka → worker pools → task DAG, idempotent outputs, retries/DLQ, priority lanes, autoscaling and hardware encoders.
  • Moderation layers hash matching (PhotoDNA/PDQ), ML classifiers and human review; ML also provides alt text.
  • A conditional post state machine gates publishing; spend expensive encodes only where views justify them.
