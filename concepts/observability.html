TL;DR
  • Monitoring tells you that something is wrong (known failure modes, dashboards, alerts); observability lets you ask new questions to find out why, without shipping new code.
  • Telemetry comes as metrics (cheap numbers over time), logs (detailed event records), traces (one request's path across services), plus profiles and change events.
  • Watch the four golden signals (latency, traffic, errors, saturation); use RED for services and USE for resources. Measure latency with percentiles from histograms — averages lie.
  • Define reliability with SLIs → SLOs → SLAs and manage it with error budgets; alert on symptoms and budget burn, page only for urgent user impact, and attach a runbook to every alert.
  • Run on-call and incident management with clear roles, and learn with blameless postmortems. Common tools: Prometheus, Grafana, ELK/OpenSearch, OpenTelemetry, Jaeger, Datadog.

1. The problem: why do we need observability?

It's 9 p.m. in Brazil, peak time. Some users report that the Instagram feed takes ten seconds to load. Somewhere among the load balancers, the API Gateway, the News Feed Service, ranking, Redis feed caches, Cassandra, the user DB, the CDN and thousands of servers in several regions, something is wrong. Questions you must answer in minutes:

  • Is it real, and how many users are affected? Only Brazil? Only Android? Only one app version?
  • Which component is slow — and is it the cause, or just a victim of something further down?
  • Did anything change recently — a deploy, a config flag, a traffic spike from a viral post?

In a monolith on one server you'd SSH in and look at the logs. In a distributed system with hundreds of services, a single user request touches dozens of machines; no human can inspect them one by one. You need the system to emit telemetry that is collected, stored and queryable centrally. That is what this lesson is about.

🧠 Analogy A car's dashboard (speed, fuel, warning lights) is monitoring: a fixed set of gauges for problems the designers anticipated. When a strange noise appears that no warning light covers, the mechanic plugs in a diagnostic computer, reads detailed sensor logs, and follows the problem through the engine — that's observability: rich enough data to investigate problems nobody predicted. A hospital adds the rest: vital-sign thresholds that page a nurse (alerting), on-call doctors (on-call), and case reviews after something goes wrong where the goal is to fix the process, not to blame the nurse (blameless postmortems).

3. The pillars of telemetry

📈 Metrics

Numeric measurements aggregated over time: request rate, error count, p99 latency, CPU %. Tiny and cheap per data point; great for dashboards and alerts; lose per-request detail.

📜 Logs

Timestamped records of discrete events with context: "user 42 upload failed: S3 timeout". Rich detail; expensive at volume.

🧵 Traces

The path of one request across services as a tree of timed spans. Show where time went and which dependency failed.

🔥 Profiles

Where CPU time and memory go inside a process, down to functions (flame graphs). Continuous profiling samples production all the time at low overhead.

🏷️ Events / changes

Deploys, config/feature-flag changes, schema migrations, failovers. Most incidents are caused by a change — overlaying change events on graphs is often the fastest diagnosis.

MetricsLogsTraces
AnswersIs something wrong? How much? Trend?What exactly happened in this event?Where in the request path is the problem?

The pillars are most powerful when linked: a latency spike on a dashboard → click through to example traces from that minute (via exemplars) → a slow span → the logs for that span (same trace_id) → the profile of the slow host.

A telemetry pipeline: services, apps and hosts emit metrics, logs and traces; collectors batch and sample them; specialised stores keep each type; dashboards query them together and alert rules page the on-call engineer.

4. Metrics in depth

4.1 Metric types

TypeWhat it isInstagram example
CounterMonotonically increasing count; you graph its rate.feed_requests_total{status="500"}
GaugeA value that goes up and down; sampled.Kafka consumer lag, Redis memory used, open WebSocket connections in the DM service.
HistogramCounts of observations in buckets (≤10 ms, ≤25 ms, ≤50 ms…); percentiles computed at query time; aggregatable across hosts.feed_request_duration_seconds_bucket
SummaryPercentiles computed in the client process.Rarely preferred — per-host percentiles cannot be averaged into a fleet percentile.

4.2 Labels and cardinality

Metrics carry labels (dimensions): http_requests_total{service="feed", endpoint="/v1/feed/timeline", status="200", region="eu"}. Each unique combination of label values is a separate time series stored by the database. Cardinality multiplies: 50 endpoints × 10 status codes × 5 regions × 2,000 hosts = 5M series. Never put unbounded values like user_id, post_id or raw URLs in metric labels — that would create billions of series and take down the metrics system. High-cardinality questions ("which user?") belong in logs and traces.

4.3 Pull vs push

Prometheus pulls ("scrapes") a /metrics endpoint on each target every 15–30 s; a target that disappears is immediately noticed (up == 0). Push systems (StatsD, OpenTelemetry OTLP, Datadog agents) have processes send metrics to a collector — better for short-lived jobs and for crossing network boundaries. Both are widely used; large fleets often combine local agents with a central, horizontally scalable TSDB.

5. What to measure: golden signals, RED and USE

5.1 The four golden signals

Google's SRE book proposes that if you can only measure four things about a user-facing system, measure these:

SignalMeaningFeed Service example
LatencyTime to serve a request — track successful and failed requests separately (a fast error is not a fast success).p50/p95/p99 of GET /feed/timeline
TrafficDemand on the system.Feed requests/s per region and app version
ErrorsRate of failed requests — explicit (5xx), implicit (200 with an empty feed), or policy (slower than 1 s counts as failure).% of feed loads returning errors or empty
SaturationHow "full" the service is — the most constrained resource; often a leading indicator.Worker-thread utilisation, queue depth, Redis CPU, connection-pool usage

5.2 RED — for request-driven services

Rate (requests/s), Errors (failed requests/s), Duration (latency distribution). Every microservice — Upload, Feed, Search, Like & Comment — gets the same three graphs per endpoint, which makes any service's dashboard instantly readable by any engineer.

5.3 USE — for resources

For every resource (CPU, memory, disk, network interface, connection pool, thread pool): Utilisation (% of time busy / % capacity used), Saturation (extra work queued that can't be served — run-queue length, swap, dropped packets), Errors (disk errors, NIC errors, OOM kills). USE finds the bottleneck; RED tells you whether users are affected.

💡 Instagram-specific signals Beyond generic RED/USE, each component has its own critical signals: Kafka consumer lag for fan-out, search-indexing and notification workers (are we falling behind?); replication lag on PostgreSQL replicas; cache hit ratio for Redis feed caches and the CDN; push delivery rate via APNs/FCM; media-processing queue age; WebSocket connection count for DMs; and client-side metrics such as app cold-start time, feed time-to-first-image and crash-free sessions.

6. Percentiles and histograms: why averages lie

A percentile pN is the value below which N% of observations fall: p50 is the median; p99 means "99% of requests were faster than this". Averages hide what users actually experience:

100 feed requests: 98 take 50 ms, 2 take 5,000 ms (stuck on a slow shard)
  average = (98×50 + 2×5000) / 100 = 149 ms        ← "looks fine"
  p50     = 50 ms
  p99     = 5,000 ms                                ← 1 in 50 users waits 5 seconds

Bimodal cache: 80% hits at 5 ms, 20% misses at 200 ms
  average = 0.8×5 + 0.2×200 = 44 ms                 ← no request ever took 44 ms!

Why the tail matters even more at Instagram's scale:

  • Volume: at 100,000 req/s, p99 describes 1,000 requests every second — real people.
  • Heavy users hit the tail most: a user loading 50 feed pages a day will see the p99 experience at least once with probability 1 − 0.9950 ≈ 40%.
  • Fan-out amplifies tails: a request waiting on 100 shards sees at least one p99 response 63% of the time (see hedged requests).

6.1 Computing percentiles correctly

You can't store every latency of 100,000 req/s forever, and you cannot average percentiles: the p99 of host A averaged with the p99 of host B is not the fleet p99. The solution is the histogram: each host counts requests into fixed buckets; bucket counts can be summed across hosts and time; the fleet percentile is estimated from the merged buckets.

latency bucket   ≤10ms  ≤25ms  ≤50ms  ≤100ms  ≤250ms  ≤500ms  ≤1s   ≤2.5s  +Inf
host A counts     120    800   2400    600      60      15     4      1      0
host B counts      90    700   2600    500      80      20     8      2      0
sum (fleet)       210   1500   5000   1100     140      35    12      3      0   total 8000
cumulative        210   1710   6710   7810    7950    7985  7997   8000
p99 → rank 7920 falls in the ≤250ms bucket (7810 < 7920 ≤ 7950) → p99 ≈ 100–250 ms (interpolate ≈ 220 ms)

Accuracy depends on bucket boundaries — choose them around your SLO thresholds. Libraries such as HdrHistogram, DDSketch and Prometheus native histograms use exponential buckets to keep relative error small (~1–2%) at any scale.

7. SLIs, SLOs, SLAs and error budgets

TermDefinitionExample for the Instagram feed
SLI — Service Level IndicatorA measured quantity that reflects user experience, usually a ratio of good events to total events.Fraction of feed requests that return successfully and within 800 ms, measured at the load balancer.
SLO — Service Level ObjectiveAn internal target for the SLI over a window.99.9% of feed requests good over a rolling 28 days.
SLA — Service Level AgreementA contract with customers with consequences (refunds/credits) if missed. Looser than the SLO.Consumer Instagram has no SLA; a paid API product (e.g. a business messaging API) might promise 99.5%.

7.1 Error budgets — worked example

An SLO of 99.9% means you are allowed 0.1% bad requests — that allowance is the error budget. Assume 10 billion feed requests per day:

28-day window: 10B × 28 = 280B requests
Error budget  = 0.1% × 280B = 280M bad requests per 28 days
In time terms = 0.001 × 28 days × 1,440 min = ~40 minutes of total outage per 28 days

Incident: a bad deploy makes 30% of feed requests fail for 20 minutes
  requests in 20 min = 10B / 1,440 × 20 ≈ 139M
  bad requests       = 30% × 139M ≈ 42M  → 15% of the 28-day budget burned

The budget turns reliability into an engineering decision instead of an argument:

  • Budget remaining → ship features, run experiments, take risks.
  • Budget exhausted → freeze risky launches, prioritise reliability work until it recovers.
  • 100% is the wrong target: users can't tell 99.99% from 100% because their own phone network fails more often than that, and every extra nine costs roughly 10× more. Pick the SLO that matches what users notice.

7.2 Burn-rate alerting

The burn rate is how fast you're consuming budget relative to plan: burn rate 1 = you'll use exactly 100% of the budget by the end of the window; burn rate 14.4 sustained for 1 hour consumes 2% of a 30-day budget. A widely used scheme (from Google's SRE workbook) uses multiple windows:

ConditionBudget consumedAction
Burn rate ≥ 14.4 over 1 h (and over last 5 min)2% in an hour🚨 Page immediately
Burn rate ≥ 6 over 6 h (and over last 30 min)5% in 6 hours🚨 Page
Burn rate ≥ 1 over 3 days10% in 3 days🎫 Ticket — fix during work hours

The short confirmation window makes the alert stop quickly once the problem is fixed; the long window prevents paging on a brief blip.

8. Logging

8.1 Structured logging

Unstructured logs ("Upload failed for user 42 after 3 retries") are readable by humans but painful to search and aggregate. Structured logs are key-value records (usually JSON) that machines can index and filter:

{
  "ts": "2026-10-23T15:42:07.118Z",
  "level": "ERROR",
  "service": "upload-service",
  "host": "upload-7f9c-eu-3",
  "region": "eu",
  "version": "2026.10.23-1",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "user_id": 184467440737,
  "event": "s3_put_failed",
  "media_id": "3192…",
  "attempt": 3,
  "error": "TimeoutError: PUT exceeded 2000 ms",
  "duration_ms": 2004
}
  • Correlation IDs: every log line carries the trace_id (and a request ID), so you can pull all logs for one request across every service.
  • Levels: DEBUG (off in production or sampled), INFO (significant business events), WARN (unexpected but handled), ERROR (a request failed), FATAL.
  • Log events, not noise: log state changes and failures with context; don't log every successful cache hit — that's what metrics are for.
  • Never log secrets or sensitive content: passwords, tokens, message bodies, full card numbers. Redact or hash PII; access to logs is itself audited (see Security).

8.2 Log pipelines

The buffer (Kafka) matters: during an incident, error logs spike 10–100×, exactly when you need the log system most. Without a buffer, the log store falls over or the agents drop logs. Cost controls: sample repetitive INFO/DEBUG logs (keep 1%, keep 100% of errors), set per-service ingestion quotas, keep only a few days in the expensive full-text index and the rest in cheap object storage queried on demand. Rough scale (assumption): 20,000 servers × 500 lines/s × 500 bytes ≈ 5 GB/s ≈ 430 TB/day before sampling — logs can easily cost more than the service itself if unmanaged.

9. Distributed tracing

Metrics say the feed is slow; logs show errors in several services. But which service made this request slow? A distributed trace records the full journey of one request through every service as a tree of timed operations.

9.1 Traces, spans and IDs

  • Trace: everything that happened for one end-to-end request, identified by a globally unique trace ID (128-bit).
  • Span: one timed operation within the trace (an RPC call, a DB query, a cache lookup) with a span ID, a parent span ID, start time, duration, status and attributes (db.system=redis, shard=17, user.app_version=312.0).
  • The parent/child links form a tree; drawn on a timeline it becomes a waterfall that shows which work was sequential, which was parallel, and where the time went.

Reading it: the gateway and auth are fine; the parallel calls are fast; the ranking call dominates, and within it the feature-store lookup takes 180 ms because its cache hit rate on shard 17 dropped from 95% to 31%. Without tracing, the ranking team, the feed team and the feature-store team would each see "slow" in their own metrics and argue about whose fault it is. With tracing, the critical path is obvious in seconds.

9.3 Context propagation

For spans from different services to join one trace, the trace context must travel with the request. The W3C Trace Context standard defines an HTTP header:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └ flags (01 = sampled)
             │  │                                └ parent span ID (the caller's span)
             │  └ trace ID (same for the whole request)
             └ version
  • Synchronous calls: tracing libraries (OpenTelemetry instrumentation for HTTP/gRPC clients and servers) read and inject the header automatically.
  • Asynchronous hops: when the Upload Service publishes "post created" to Kafka, the context goes into the message headers; the fan-out worker that consumes it starts a span linked to the producer's span. Now you can trace "user posted → fan-out → push notification delivered" end to end.
  • In-process: context must follow the request across thread pools and async callbacks — a common source of broken traces.
  • Baggage: small key-values propagated alongside (e.g. experiment=881) so deep services can tag their telemetry. Keep it tiny; it travels on every hop.

9.4 Sampling

Recording every span of every request is too expensive (a feed request might produce 50+ spans; at 100k req/s that's 5M spans/s). So traces are sampled:

Head-based samplingTail-based sampling
Decision madeAt the start of the request (e.g. keep 1%), propagated in the traceparent flags so all services agree.After the trace completes, by a collector that buffers all spans briefly.
ProsCheap and simple; no buffering.Can keep the interesting traces: all errors, all slow (> p99) requests, plus a small random baseline.
ConsRare errors are mostly discarded (99% of them with 1% sampling).Needs to collect every span temporarily — expensive infrastructure.

Practical systems combine them: head-sample a baseline, always keep errors and very slow requests, and allow forced tracing for specific debugging (e.g. an engineer's own account or a flagged request).

10. Alerting

10.1 Symptom-based vs cause-based

Alert on symptoms users feel ("feed error rate above SLO burn threshold", "DM delivery p99 > 5 s"), not on every possible cause ("CPU > 80% on host 1234", "one Cassandra node down"). Causes are many and often harmless (a host at 85% CPU serving fine; a replica down with others healthy); symptoms are few and always matter. Cause metrics belong on dashboards for diagnosis. Exceptions: causes that predict imminent user impact without a symptom yet — "disk will be full in 4 hours", "certificate expires in 7 days", "Kafka consumer lag growing for 30 min".

10.2 Pages vs tickets

Page 🚨Ticket 🎫
WhenUsers are hurt now or will be within hours; needs a human immediately.Needs attention, but within a business day is fine.
ExamplesFast error-budget burn, upload success < 99%, region unreachable, notification pipeline stalled.Slow budget burn, a single host's disk degrading, backup job failed once, certificate expiring in 3 weeks.
DeliveryPhone call / push via PagerDuty or Opsgenie, escalates if unacknowledged.Queue in the team's issue tracker.

10.3 Runbooks

Every alert should link to a runbook: what the alert means, the likely causes, the dashboards and queries to check, safe mitigation steps (roll back the last deploy, drain a region, enable degraded mode, flip a kill switch), and who to escalate to. A tired engineer at 4 a.m. should not have to reverse-engineer an alert.

# Prometheus alert rule: fast burn of the feed availability SLO (99.9%)
- alert: FeedSLOFastBurn
  expr: |
    (sum(rate(feed_requests_total{status=~"5.."}[1h])) / sum(rate(feed_requests_total[1h])))  > (14.4 * 0.001)
    and
    (sum(rate(feed_requests_total{status=~"5.."}[5m])) / sum(rate(feed_requests_total[5m]))) > (14.4 * 0.001)
  labels:
    severity: page
    team: feed
  annotations:
    summary: "Feed is burning its error budget 14x too fast"
    runbook: "wiki/runbooks/feed-slo-fast-burn"
    dashboard: "grafana/d/feed-overview"

10.4 Alert fatigue

When engineers receive dozens of alerts per shift, most of them unactionable or duplicates, they start ignoring them — and miss the real one. This is alert fatigue. Remedies:

  • Every page must be actionable, urgent and real; delete or downgrade alerts that are routinely acknowledged and ignored.
  • Group and deduplicate (one page for "Redis cluster degraded", not 64 pages for 64 shards); add inhibition rules (don't page for every service when the region is down).
  • Require a minimum duration (for: 5m) to skip brief blips; use burn-rate alerts instead of raw thresholds.
  • Review alert statistics in a weekly on-call handover; track pages per shift as a team health metric (a common target: no more than ~2 incidents per 12-hour shift).

11. Dashboards

Dashboards are for humans to understand state quickly. Good practice:

  • Hierarchy: a top-level "Instagram health" board (SLOs per user journey: open app, load feed, post, send DM, view story) → per-service RED boards → per-resource USE boards → drill-down queries.
  • Same layout for every service (RED at the top, dependencies' RED next, saturation below) so on-call engineers can read any team's board.
  • Overlay change events (deploys, flag flips, failovers) as vertical markers.
  • Show percentiles and rates, not averages and raw counters; compare to the same time last week to separate daily patterns from anomalies.
  • Break down by key dimensions: region, app version, platform (iOS/Android/web), endpoint — most incidents are localised to one of these.
  • Avoid "wall of 200 graphs" dashboards — nobody can read them under pressure.

12. On-call, incident management and postmortems

12.1 On-call

Each service team runs an on-call rotation: one primary (and a secondary backup) responsible for responding to pages, typically for a week at a time, often "follow-the-sun" across time zones so nobody is woken at night routinely. Healthy on-call has manageable page volume, good runbooks, the authority to roll back, and time after a rough shift to fix the root causes.

12.2 Incident management

  1. Detect: alert fires or users report a problem.
  2. Declare & triage: open an incident, assign a severity (SEV1 = major user-facing outage, e.g. feed down in a region; SEV3 = minor degradation).
  3. Assign roles: Incident Commander (coordinates, decides — doesn't debug), Operations/Tech lead (hands on keyboard), Communications lead (status page, internal updates), Scribe (timeline).
  4. Mitigate first, root-cause later: roll back the deploy, drain the region, turn off the feature flag, enable degraded mode. Restoring users comes before understanding.
  5. Resolve & monitor: confirm metrics are back to normal; keep watching.
  6. Postmortem within days.

12.3 Blameless postmortems

A postmortem is a written analysis of an incident. Blameless means it assumes everyone acted reasonably given the information and tools they had, and asks "how did the system allow this?" rather than "who messed up?". If people are punished for mistakes, they hide them, and the organisation stops learning. A typical template:

SectionExample content
Summary & impact"For 23 minutes, 18% of feed loads in South America failed; ~40M requests affected; 9% of 28-day error budget consumed."
TimelineDetection time, key decisions, mitigation, resolution (from the scribe's notes and telemetry).
Root cause(s) & contributing factorsA config change raised the feature-store cache TTL; a hot shard evicted keys; no canary for config changes; alert fired 9 minutes after impact began.
What went well / badly / luckyRollback was fast; dashboards lacked per-shard breakdown; the issue started off-peak.

  • SLIs measured at the edge and in the app. Server-side metrics can't see failures that happen before the request arrives (DNS, TLS, mobile network) or after (image decode, rendering). So user-journey SLIs — "feed loaded with first image visible", "photo posted successfully", "DM delivered" — are computed from both load-balancer logs and client telemetry (see Clients).

  • Every deploy is an event: Instagram's engineering talks describe continuous deployment of its large Python/Django service through canary stages, where automated checks compare error rates and latency of the canary against the rest of the fleet and halt the rollout on regressions. 14. Trade-offs & common pitfalls

✅ Benefits

  • Detect problems before (or as soon as) users notice
  • Diagnose in minutes instead of hours (lower MTTR)
  • Objective reliability targets (SLOs) that balance speed and stability
  • Safe continuous deployment via canary analysis
  • Capacity planning and performance optimisation from real data

⚠️ Costs

  • Telemetry storage and processing can rival the cost of the service
  • Instrumentation overhead (CPU, latency, code)
  • Cardinality explosions can take down the metrics system
  • Sampling loses data; logs may leak sensitive information
  • Badly tuned alerts burn out on-call engineers

Common pitfalls

  • Averages instead of percentiles; averaging per-host percentiles.
  • Unbounded label values (user_id, URL) in metrics.
  • Alerting on causes (CPU, single hosts) instead of user-facing symptoms → noise and fatigue.
  • Alerts without runbooks or without an owner.
  • Only server-side measurement — missing failures in DNS, the network, or the app.
  • Broken trace propagation across async boundaries (Kafka, thread pools) → fragmented traces.
  • The monitoring system depends on the system it monitors (same region, same Kafka): when production fails, observability fails with it. Run monitoring out-of-band and alert on "no data".
  • Logging PII or secrets; keeping logs forever.
  • Blame-oriented postmortems that make people hide mistakes.

16. Interview corner

How would you monitor Instagram's feed service? What would you alert on?

Define user-journey SLIs: fraction of feed loads that succeed and render within, say, 800 ms (measured at the LB and from client telemetry). SLO 99.9% over 28 days. Dashboards: RED per endpoint broken down by region/platform/app version; dependency RED (Redis timeline, ranking, counters, user service); saturation (worker utilisation, queue depth, connection pools); cache hit ratio; fan-out Kafka lag; deploy markers. Alerts: multi-window burn-rate pages on the SLO; tickets for slow burn; a few predictive cause alerts (lag growing, disk full ETA). Every alert has a runbook. Traces with tail-sampling of slow/error requests and structured logs carrying trace IDs for diagnosis.

Why are percentiles better than averages, and how do you compute a fleet-wide p99?

Averages hide the tail and multimodal distributions — 2% of requests at 5 s barely move the mean but ruin the experience for millions of users, and fan-out turns per-call tails into common request-level latency. Percentiles can't be averaged across hosts, so each host records a histogram (bucket counts); you sum bucket counts across hosts and time windows and estimate the p99 from the merged cumulative distribution, with bucket boundaries chosen around the SLO thresholds (or with exponential/sketch histograms like DDSketch for bounded relative error).

Explain SLI, SLO, SLA and error budgets with numbers.

SLI: good requests / total, e.g. feed loads that succeed within 800 ms. SLO: 99.9% over 28 days. With 10B requests/day the budget is 0.1% × 280B = 280M bad requests (≈ 40 minutes of full outage). SLA: an external contract with penalties, set looser than the SLO (e.g. 99.5%), typically for paid APIs. If an incident burns 15% of the budget, that's fine; if the budget is exhausted, risky launches freeze and reliability work takes priority. Alert on burn rate (14.4× over 1 h pages) rather than raw error thresholds.

How does distributed tracing work across services and Kafka?

The first service creates a trace ID and a root span; each outgoing call injects a traceparent header (trace ID, parent span ID, sampled flag); each receiving service extracts it, creates child spans and propagates further. For Kafka, the context is written into message headers, and the consumer starts a span linked to the producer's span. Spans are exported asynchronously to a collector, sampled (head-based baseline plus tail-based keep-all-errors/slow), and assembled into a waterfall in Jaeger/Tempo. Logs include the trace ID for cross-referencing.

What makes a good alert? How do you fight alert fatigue?

Good alerts are symptom-based (user impact), urgent, actionable, owned, and linked to a runbook and dashboard. Fight fatigue by deleting alerts that don't lead to action, converting non-urgent ones to tickets, using burn-rate alerts with confirmation windows, grouping and inhibiting related alerts, and reviewing page statistics every on-call handover with a budget for pages per shift.

Walk through how you'd run an incident and what happens afterwards.

Declare an incident and severity; assign an incident commander, ops lead, comms lead and scribe; open a shared channel and timeline. Focus on mitigation first — roll back recent changes, drain the affected region/cell, enable degraded modes — using dashboards, traces and change logs to localise. Communicate status regularly. After resolution, write a blameless postmortem within days: impact, timeline, root and contributing causes, what went well/badly, and owned action items (e.g. better canaries, new alerts, runbook fixes), tracked to completion.

17. Check your understanding

Your SLO is 99.95% over 30 days for 2B requests/day. How many failed requests is your error budget? How many minutes of complete outage is that?

Requests = 2B × 30 = 60B; budget = 0.05% × 60B = 30M failed requests. Time-wise: 0.0005 × 30 × 1,440 = 21.6 minutes of total outage.

Host A reports p99 = 120 ms and host B reports p99 = 400 ms, with equal traffic. Is the fleet p99 260 ms?

No. Percentiles can't be averaged. The fleet p99 depends on the full distributions: if B's slow requests make up most of the slowest 1% overall, the fleet p99 could be close to 400 ms or above. Merge histogram buckets from both hosts and compute the percentile from the combined distribution.

An engineer adds user_id as a label to the feed latency histogram with 12 buckets. With 500M daily users, what happens?

Each user creates ~14 new series (12 buckets + sum + count) → ~7 billion time series — a cardinality explosion that would overwhelm the metrics backend. Per-user questions belong in logs/traces (high-cardinality stores), or use bounded dimensions (region, app version, platform).

Which should page someone at 3 a.m.: (a) CPU at 90% on one feed host, (b) feed error budget burning at 20× for 10 minutes, (c) a backup job failed once, (d) Kafka fan-out lag growing steadily for 45 minutes?

(b) definitely — active user impact burning budget fast. (d) likely — it predicts imminent impact (new posts not reaching feeds) and won't fix itself. (a) is a cause with no proven user impact → dashboard/ticket. (c) → ticket for the next business day (unless backups have been failing repeatedly).

With 1% head-based trace sampling, an error affects 0.05% of requests at 100k req/s. How many error traces per minute do you capture? How would tail-based sampling change this?

Errors: 0.0005 × 100,000 = 50/s = 3,000/min; with 1% head sampling you keep only ~30 per minute (and possibly fewer if the error affects only certain users). Tail-based sampling that keeps all error traces would capture all ~3,000/min (or a capped subset), making rare errors much easier to diagnose.

In a trace, the feed request takes 900 ms. Spans: Redis 5 ms, counters 30 ms and user service 25 ms (parallel), ranking 820 ms of which feature store 760 ms. Where do you look first, and why not at the counters service even though it logged errors?

The feature store inside ranking — it's on the critical path and accounts for ~85% of the latency. The counters service's errors may be real but it ran in parallel for only 30 ms (and presumably has a fallback), so it isn't what made this request slow. Tracing's value is precisely identifying the critical path.

Why should your monitoring and alerting stack not run only in the same region and on the same Kafka cluster as production?

Because the failures you most need to see — a regional outage or a Kafka failure — would also take down your telemetry, leaving you blind exactly when it matters. Run monitoring out-of-band (another region/provider), use external synthetic probes, and alert on missing data ("no metrics received").

🎯 Key takeaways
  • Monitoring detects known problems; observability lets you investigate new ones. You need both.
  • Use the right signal: metrics for trends/alerts, logs for detail, traces for the request path, profiles for code hot spots, change events for "what changed?".
  • Measure with golden signals, RED and USE; use percentiles from mergeable histograms, never averages; avoid unbounded label cardinality.
  • Set SLOs on user-facing SLIs, spend error budgets deliberately, and alert on burn rate.
  • Propagate trace context everywhere (including Kafka) and sample smartly (keep errors and slow traces).
  • Page only for urgent symptoms with runbooks; run incidents with clear roles; learn with blameless postmortems.
