TL;DR
  • Back-of-the-envelope estimation = quick, rounded arithmetic that tells you the order of magnitude of load, storage, bandwidth and hardware, so you can justify design decisions.
  • Memorise a few anchors: 1 day ≈ 86,400 s ≈ 105 s; 1M/day ≈ 12/s; 1 PB/day ≈ 12 GB/s ≈ 93 Gbps; powers of two (210 ≈ 103); and latency numbers (memory ~100 ns, same-DC round trip ~0.5 ms, cross-continent ~150 ms).
  • Method: assumptions → rates (QPS) → sizes (storage, bandwidth) → resources (servers, shards, cache nodes) → sanity check. Always compute average and peak (2–3×).
  • Instagram under our assumptions: ~1.2K posts/s, ~116K feed reads/s (~350K peak), ~1.1M API req/s peak, ~580 TB/day new media (~212 PB/year logical), ~85 PB/day egress (~8 Tbps) mostly served by the CDN, ~9 TB of cache, ~1.5 GB/s into Kafka.
  • The numbers are the argument: they prove you need a CDN, object storage, sharding, caching and async fan-out.

1. The problem: why estimate at all?

Should Instagram's feed be served from the database or from a cache? Will one PostgreSQL server hold all the posts? Do we need a CDN? You cannot answer any of these by intuition alone. "A lot of users" might mean 1,000 requests per second (one server is fine) or 1,000,000 (you need thousands of servers and a completely different design). Estimation turns vague scale into numbers you can reason with — in two to five minutes, with mental arithmetic.

Estimates are useful precisely because they are rough. Nobody cares whether storage is 580 TB/day or 610 TB/day; what matters is that it's "hundreds of terabytes per day", which immediately means "not in a relational database, use object storage", and "over 200 petabytes per year", which means "storage cost and tiering are first-class concerns". Getting the exponent right is the whole game; the leading digit is a bonus.

Real engineers do this constantly: capacity planning before a launch, checking whether a proposed design can possibly meet its latency target, sanity-checking a cloud bill. Interviewers use it to see whether you can connect requirements to architecture with evidence.

🧠 Analogy Planning a wedding. You don't know exactly how many guests will come, but you estimate: ~200 invited, ~80% attend → ~160 people; each eats ~0.5 kg of food → ~80 kg; 10 per table → 16 tables; a bus holds 50 → 4 buses. Every number is approximate, but it's good enough to book the right venue, order roughly the right food and not hire a single taxi for 160 people. If you'd guessed "maybe 20 guests", you'd have booked the wrong building. Capacity estimation is the same: roughly right beats precisely wrong.

A few practical system-level numbers to add to the classic list (orders of magnitude, assume rather than quote):

  • Redis/Memcached GET inside a data centre: ~0.2–1 ms (mostly network). One node: ~100K+ simple ops/s.
  • Indexed lookup in a well-tuned SQL database (hot in buffer cache): ~1–5 ms; a single primary handles roughly 5K–20K writes/s depending on hardware and row size.
  • Cassandra-style node: ~10K–50K writes/s; comfortable data per node ~1–2 TB (to keep compaction and repair manageable).
  • TCP + TLS 1.3 handshake to a server 100 ms away: ~2 round trips ≈ 200 ms before the first byte — which is why connection reuse and edge termination matter (Networking).
  • A modern server NIC: 10–100 Gbps. A Kafka broker: ~100 MB/s of sustained produce traffic per broker is a conservative planning number.

3. The estimation method

Estimation is a pipeline: each stage multiplies the previous one by a rate or a size. Sanity checks close the loop.
  1. State assumptions explicitly and round them to friendly numbers (500M not 487M). Write them on the board.
  2. Convert per-day counts into per-second rates, separately for reads and writes. Multiply by a peak factor (2–3×).
  3. Multiply counts by sizes to get storage (per day, per year, over the retention period) and bandwidth (in and out). Remember replication and multiple renditions.
  4. Divide by per-machine capacity to get server, shard and cache-node counts. Add headroom (target ~60–70% utilisation) and redundancy (survive losing a zone).
  5. Sanity-check and, most importantly, say what the number means for the design.
💡 Arithmetic tricks Work in scientific notation and add exponents: 500M × 20 = 5×108 × 2×101 = 10×109 = 1010. Then 1010 / 105 = 105 = 100K/s. Keep one significant digit until the end. Label units on every line (requests/day, bytes/s) — unit mistakes are the most common error.

4.3 Fan-out write amplification

With push-based fan-out (News Feed), every post is inserted into each follower's timeline:

timeline inserts/day = 100M posts × 200 followers (avg) = 2 × 10^10 = 20B/day
average  = 20B / 86,400 ≈ 231K inserts/s
peak     ≈ 700K inserts/s

Optimisation: only fan out to followers active in the last ~30 days.
If ~25% of edges point to recently active users → ~5B/day ≈ 58K/s average.
Celebrities (say >1M followers) are excluded and pulled at read time —
one 500M-follower post would otherwise be 500M inserts on its own.

So each 1 post/s of writes becomes ~200 timeline writes/s — the "small" write rate is amplified 200× inside the system.

On a log scale the difference is stark: metadata is "big data", media is "enormous data".

How many edge servers? If one edge cache server can serve ~40 Gbps of real traffic, peak ~24 Tbps needs at least ~600 servers — and in practice many more, because traffic must be served from hundreds of locations near users, each sized for its local peak plus failover. That's why at this scale companies either buy from the largest CDN providers or, like Meta, build their own edge network.

4.8 Cache memory sizing (the 80/20 rule)

The Pareto (80/20) rule says ~20% of items receive ~80% of requests. So caching the hottest ~20% of the data gives a high hit ratio at a fraction of the memory. There are two ways to size a cache; the second is more reliable.

(a) The classic interview formula — and its trap:

cache ≈ 20% × (read requests/day × response size)
      = 0.2 × 10B feed pages × 20 KB = 40 TB      ← overestimate!

This counts the same popular post millions of times. Caches store distinct objects, so size by distinct hot objects instead.

(b) Bottom-up, per data structure:

Cached dataCalculationMemory
Feed timelines (post IDs + scores) for DAU500M users × 500 entries × 16 B = 4 TB; × ~2 for data-structure overhead~8 TB
Hot post metadata (80/20)~1B distinct posts viewed/day × 1 KB = 1 TB; cache hottest 20%~200 GB
User profiles of DAU500M × 1 KB~500 GB
Like/comment counters for hot posts1B posts × ~50 B (key + 2 counters + overhead)~50 GB
Sessions / auth tokens500M × 200 B~100 GB
Total~9 TB
Nodes by memory:     9 TB / ~50 GB usable per node (on a 64 GB box) ≈ 180 primaries
Nodes by throughput: feed hydration ≈ 350K pages/s × ~20 lookups = 7M ops/s (peak)
                     + fan-out inserts ~0.7M/s  ≈ 8M ops/s ÷ ~100K ops/s per node ≈ 80 nodes
→ memory is the binding constraint: ~180 primaries, ×2 with one replica each ≈ 360 cache nodes

What it means: the entire hot working set fits in a few hundred RAM-heavy machines — which is why serving the feed from Redis is feasible at all. Note the timelines dominate; capping them (e.g. 500 entries, older items fetched on demand) is a key cost lever.

5. Sanity-check techniques

Estimates go wrong by factors of 1,000 through a single slipped unit. Before you rely on a number, check it with at least one of these:

  1. Per-user check. Divide the total by the number of users. 85 PB/day ÷ 500M DAU = 170 MB per user per day — about 30 short videos plus 100 photos. Plausible for a heavy media app on mobile. If you'd got 170 GB per user per day, something is off by 1,000×.
  2. Per-machine check. Does any single box need to do something impossible? "One database handling 350K reads/s" or "one server pushing 8 Tbps" → wrong design or wrong number.
  3. Two methods. Compute top-down (DAU × actions) and bottom-up (requests per screen × screens per session × sessions). If they disagree by more than ~3×, find out why.
  4. Ratios. Does the read:write ratio match the product's nature? Does egress:ingress (~140:1) fit "each post viewed hundreds of times"?
  5. Known anchors. Compare with physical limits you know: a 100 Gbps NIC, a ~2 TB comfortable DB node, ~100K ops/s per Redis node, 86,400 seconds per day.
  6. Units on every line. Bits vs bytes (×8), per day vs per second (×86,400), KB vs MB (×1,000). Write the unit next to every number.
  7. Order-of-magnitude rounding. If rounding an input up or down by 2× changes your design decision, the decision is sensitive — say so and pick the safe side.

Do the maths: 213 = 8,192 logical shards; 210 = 1,024 IDs per shard per millisecond → ~1M IDs per second per shard; 241 ms ≈ 69.7 years of timestamps. Those bit widths are a capacity estimate frozen into a format (see ID Generation). Second, the decision to create thousands of logical shards up front and map them onto a small number of physical PostgreSQL servers was explicitly about growth: moving a logical shard to a new machine is easy; re-splitting data later is hard. Both decisions came from asking "how big will this get?" before it got big.

8. Trade-offs & common pitfalls

✅ Why estimation is worth it

  • Turns "it needs to scale" into specific, defensible decisions
  • Catches impossible designs early (one DB at 350K QPS)
  • Reveals which constraint binds: storage, RAM, CPU or network
  • Identifies the biggest cost drivers (video storage, egress)
  • Quick: 3–5 minutes with mental arithmetic

⚠️ Limits

  • Garbage in, garbage out — assumptions dominate the result
  • Averages hide skew (celebrities, viral posts, hot shards)
  • Per-server capacity numbers vary 10× by language and workload
  • Easy to burn interview time on precision nobody needs
  • Real capacity planning needs load tests and production metrics

Common mistakes

  • Bits vs bytes. 1 Gbps is 125 MB/s, not 1 GB/s — an 8× error.
  • Forgetting peak. Sizing for the average means falling over every evening.
  • Forgetting replication and renditions. Raw storage is 1.5–3× logical; each photo exists in 4–8 sizes/formats; videos in a whole bitrate ladder.
  • Forgetting write amplification. 1 post = ~200 timeline writes, plus index updates, plus replicas.
  • Mixing up DAU and MAU, or using MAU to size daily traffic.
  • Over-precision. "1,157.407 QPS" wastes time and signals the wrong priorities. Say "~1.2K/s".
  • Computing numbers that drive nothing. Every estimate should end with "…therefore we need X".
  • The naive 80/20 cache formula applied to request volume rather than distinct objects (overestimates by orders of magnitude).
  • Ignoring the skew. The average user has 200 followers; the top account has hundreds of millions. Hot keys, not averages, break systems.
  • Not saying "assume". Present inputs as assumptions, not as facts about a real company.

10. Interview corner

Estimate the peak QPS of Instagram's home feed.

Assume 500M DAU, each loading ~20 feed pages a day (opening the app several times and scrolling). That's 10B pages/day. Divide by ~86,400 s: ~116K/s average. Traffic is uneven through the day, so peak ≈ 3× → ~350K/s. Implication: we can't compute feeds from the database per request; timelines must be pre-computed and kept in memory, with each page hydrated from caches.

How much storage does Instagram need for new media per year?

Assume 100M posts/day: 85M photos at ~1.5 MB including renditions (~128 TB/day) and 15M videos at ~30 MB including the bitrate ladder (~450 TB/day) → ~580 TB/day, ~212 PB/year logical. With erasure coding (~1.5×) that's ~320 PB raw per year, or ~640 PB with 3× replication. Conclusions: object storage, not databases; video dominates (~78% of bytes); cold-tiering old media is the biggest cost lever.

How would you size the Redis cluster for feed timelines?

Store, per active user, the latest ~500 post IDs with a score: 500 × 16 B = 8 KB, ~16 KB with data-structure overhead. For 500M DAU that's ~8 TB. Add hot post metadata (~200 GB by 80/20 on distinct posts), profiles (~500 GB) and counters (~50 GB): ~9 TB total. At ~50 GB usable per node → ~180 primaries, ~360 nodes with replicas. Check throughput too: ~8M ops/s peak ÷ ~100K ops/s per node ≈ 80 nodes — so memory, not throughput, is the binding constraint.

Why is it misleading to say Instagram has a read:write ratio of 100:1?

Because it depends on what you count. At the API level, likes and DMs are frequent writes, so reads:writes is only ~3:1 under our assumptions. At the content level, each post is viewed ~1,000 times (100B impressions vs 100M posts per day), and media bytes out vs in is ~140:1. The content ratio justifies caching, pre-computed feeds and CDNs; the API ratio warns that the like path needs a write-optimised design.

How many app servers do you need, and what's the weakest assumption?

Peak ~1.1M API requests/s. If one server handles ~1,000 req/s, that's 1,100 servers; at a 70% utilisation target ~1,570; to survive losing one of three zones, ×1.5 → ~2,400. The per-server throughput is the weakest assumption — it varies from ~200 req/s (an interpreted language with many downstream calls) to several thousand. I'd replace it with a load-test number as soon as possible, and note that halving per-request work halves the fleet.

How do you estimate Kafka capacity for Instagram?

Domain events ≈ total writes ≈ 91K/s × ~1 KB ≈ 91 MB/s average. Client analytics events dominate: ~250B/day ≈ 2.9M/s × 500 B ≈ 1.45 GB/s. With RF 3 and peak 3×, brokers write ~14 GB/s; at ~100 MB/s per broker that's ~140 brokers, ~150–200 with headroom, preferably in separate clusters so analytics floods don't delay fan-out. Partition counts follow consumer parallelism (e.g. 128–256 for post events). Retention × throughput × RF gives disk: ~165 TB for 7 days of domain events.

How do you decide the number of Cassandra nodes for posts, likes and comments?

Compute both constraints. Storage: ~183 TB/year logical × 5 years × RF 3 ≈ 2.7 PB; at ~2 TB per node ≈ 1,400 nodes. Throughput: ~195K writes/s peak × RF 3 ≈ 585K replica writes/s; at ~20K per node ≈ 30 nodes. Storage binds, so ~1,400 nodes; the levers are compression, shorter retention for derived data (like rows could be compacted into counts for old posts), and tiering.

11. Check your understanding

Numeric: 300M events per day. Average events per second?

300M ÷ 86,400 ≈ 3,500/s (shortcut: 1M/day ≈ 12/s → 300 × 12 ≈ 3,600/s). Peak ≈ 7–10K/s.

Numeric: a service sends 2 PB per day. What's that in Gbps?

1 PB/day ≈ 11.6 GB/s ≈ 93 Gbps, so 2 PB/day ≈ 23 GB/s ≈ ~185 Gbps average.

Why can't Instagram's user ID be a signed 32-bit integer?

231 − 1 ≈ 2.1 billion — barely above ~2B users and far below the number of posts, likes or messages. IDs must be 64-bit (max ≈ 9.2 × 1018).

Numeric: Your CDN hit ratio improves from 95% to 99%. By how much does origin egress fall?

Misses fall from 5% to 1% of requests — a 5× reduction (from ~4.25 PB/day to ~0.85 PB/day for 85 PB/day of egress).

Scenario: a candidate says "cache = 20% of daily read traffic = 40 TB". What's wrong?

The 80/20 rule applies to distinct objects, not request volume. 10B feed responses mostly reference the same popular posts; caching each response separately would duplicate them. Size by distinct hot items (timelines per DAU, hot posts, profiles) → ~9 TB here.

Numeric: 100M posts/day, average 200 followers each, push fan-out. Timeline inserts per second?

100M × 200 = 20B/day ÷ 86,400 ≈ 231K inserts/s average (~700K/s peak). That's ~200× the post rate — the write amplification of fan-out on write.

Using the "human-scale" latency analogy, why is a feed request that makes 20 sequential DB calls slow?

Each same-DC round trip is ~0.5 ms (plus query time ~1–5 ms) — an eternity relative to memory access. 20 sequential calls ≈ 20–100 ms just waiting, before any tail effects. Batch or parallelise the calls and read from in-memory caches.

You compute 170 GB of media egress per user per day. What should you do?

Sanity-check: that's hours of 4K video per user per day — implausible for an average user. Look for a unit slip (KB vs MB, or per-day vs per-second). The intended estimate here is ~170 MB per user per day.

🎯 Key takeaways
  • Estimation is about orders of magnitude — round aggressively, state assumptions, label units.
  • Anchors: 105 s/day, 1B/day ≈ 12K/s, 1 PB/day ≈ 93 Gbps, 210 ≈ 103, RAM ≪ SSD ≪ network ≪ cross-continent.
  • Method: assumptions → rates → sizes → resources → sanity check; always include peak, replication, renditions and write amplification.
  • Instagram: ~1.2K posts/s but ~350K feed reads/s peak; ~580 TB/day new media; ~8 Tbps egress → CDN; ~9 TB cache; ~1.5 GB/s Kafka.
  • Compute every constraint (storage, throughput, RAM) — the tightest one sets the machine count.
  • Always finish with "…therefore the design needs X".
