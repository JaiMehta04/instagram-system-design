TL;DR
  • Scalability = handling more load by adding resources. Prefer horizontal scaling of stateless services; the scale cube gives three ways to scale: clone (X), split by function (Y), split by data (Z).
  • Availability = fraction of time/requests the system works. Components in series multiply availabilities (worse); redundant components in parallel give 1 − Π(1 − Ai) (better). Remove every single point of failure; fail over automatically (active-passive or active-active).
  • Reliability (correct behaviour), availability (up), durability (data never lost) and fault tolerance (keeps working despite failures) are related but different.
  • Performance: latency vs throughput; measure p50/p95/p99, not averages. Fan-out amplifies tail latency: with 100 backends each 1% slow, 63% of requests are slow. Little's law L = λW links concurrency, throughput and latency.
  • Also design for maintainability/operability and cost. Every box in the Instagram diagram exists to buy one or more of these properties.

1. The problem: why do we need these principles?

Instagram's requirements (see Requirements) say: serve 500M people a day, at ~350K feed requests per second at peak, with p99 latency under 300 ms, 99.99% availability, and never lose a photo. Now imagine the simplest possible implementation: one server running the app and a database, with photos on its disk. Every one of those requirements fails:

  • Scale: one server handles maybe a few thousand requests per second — two orders of magnitude short.
  • Availability: when that server reboots for a kernel patch, Instagram is down for everyone.
  • Durability: when its disk dies, every photo ever posted is gone.
  • Performance: users in Mumbai wait 300 ms just for packets to reach Virginia and back, before any work is done.

The principles in this lesson are the vocabulary for describing how a design fixes each of these — and what it costs. They come up in every system design interview, usually in step 6 ("what are the bottlenecks and failure modes?" — see How to Approach).

🧠 Analogy A restaurant. Scalability: when more customers come, you hire more cooks (horizontal) or buy a bigger oven (vertical), or open more branches. Availability: the restaurant is open even when one cook is sick — because no dish depends on a single person. Reliability: the food that comes out is what was ordered, every time. Durability: the secret recipes are written down in a safe and a copy is kept at the bank — a kitchen fire doesn't destroy them. Performance: how long you wait for your meal (latency) and how many meals the kitchen serves per hour (throughput). Maintainability: a new cook can learn the kitchen in a week. Cost: the restaurant still makes a profit.

2. Scalability

Scalability is a system's ability to handle increased load — more users, more data, more requests — by adding resources, while keeping performance acceptable. A scalable system's capacity grows roughly in proportion to the resources you add. "Load" must be described with load parameters: for Instagram, requests per second per endpoint, read:write ratio, follower-count distribution, data volume.

2.1 Vertical vs horizontal scaling

Scaling up buys a bigger machine; scaling out adds more machines behind a load balancer.
Vertical scaling (scale up)Horizontal scaling (scale out)
HowBigger machine: more CPU, RAM, faster disksMore machines sharing the load
Code changesNoneServices must be stateless or data must be partitioned
LimitHard ceiling (largest available machine); cost grows super-linearly near the topPractically unlimited; cost grows ~linearly
AvailabilityStill a single point of failureRedundant: losing one of N machines loses 1/N capacity
Operational complexityLowHigher: load balancing, distributed data, partial failures
UpgradesUsually downtime to resizeRolling: add/replace machines one at a time
Best forEarly stage; databases that are hard to distribute; quick reliefStateless tiers; anything at Instagram scale

Real systems do both: scale up a database primary to the largest sensible machine (it buys time and simplicity), and scale out everything else. Instagram's early story, as told in public talks, followed this path: a few bigger servers first, then many servers and sharded databases as growth demanded.

2.2 Stateless services: the key to scaling out

A service is stateless when it keeps no client-specific data in its own memory or disk between requests: any instance can handle any request. All state lives in shared external stores — databases, caches, object storage. Then:

  • The load balancer can send each request to any healthy instance (no "sticky sessions").
  • Adding capacity = starting more instances; autoscaling becomes trivial.
  • An instance crashing loses nothing except in-flight requests, which clients retry.
  • Deploys are rolling restarts with zero downtime.
# ❌ Stateful: session kept in the server's memory — breaks when the LB picks another server
sessions = {}                                   # lives in this process only
def login(user):  sessions[token] = user
def feed(token):  user = sessions[token]        # KeyError on any other instance

# ✅ Stateless: identity carried in a signed token, data in shared stores
def feed(request):
    user_id = verify_jwt(request.headers["Authorization"])   # no server memory needed
    post_ids = redis.zrevrange(f"timeline:{user_id}", 0, 19)
    return hydrate(post_ids)                                  # from cache / Cassandra

In the Instagram diagram every application service (Upload, Feed, Like & Comment, Follow, Search, User/Auth) is stateless. The one notable exception is the Direct Messaging WebSocket tier, which must hold long-lived connections; it keeps only the connection itself in memory and stores everything else (messages, presence) externally, with a routing table saying which gateway holds which user's connection. See Microservices & Stateless Services.

2.4 Scaling the data tier

Stateless compute is the easy part; data is where scaling gets hard, because it has state by definition.

  • Read-heavy? Add caches (absorb most reads) and read replicas (X-axis for reads). Instagram's ~100:1 content read ratio makes this the first lever.
  • Too much data or too many writes for one machine? Shard (Z-axis), ideally with consistent hashing or many logical shards so you can rebalance.
  • Different access patterns? Use different stores for different data (polyglot persistence): PostgreSQL for users, Cassandra for posts, Redis for timelines, Elasticsearch for search, S3 for media (Databases).
  • Expensive work on the request path? Move it off via a queue (Kafka) and process asynchronously — this scales the work independently of user-facing latency.
💡 Elasticity vs scalability Scalability is the ability to grow capacity; elasticity is doing it automatically and quickly in response to load (autoscaling), and shrinking again to save money. Stateless tiers can be elastic in minutes; stateful tiers (databases, caches) usually scale in planned steps because data must be moved.

3. Availability

Availability is the proportion of time — or, better at scale, the proportion of requests — for which the system is working correctly:

availability (time-based)    = uptime / (uptime + downtime)
availability (request-based) = successful requests / total valid requests
availability (from failures) = MTBF / (MTBF + MTTR)
   MTBF = mean time between failures   MTTR = mean time to recovery (detect + fix)

The last formula reveals the two levers: fail less often (raise MTBF) or recover faster (cut MTTR). At scale, recovering faster is usually far cheaper. Example: a component fails once a month (MTBF = 720 h). If a human must notice and fix it (MTTR = 1 h), availability = 720/721 = 99.86%. If automatic failover recovers in 1 minute, availability = 720/(720 + 0.0167) = 99.998% — the same unreliable hardware, 60× less downtime.

Each extra nine is 10× less downtime, and typically costs far more than 10× the engineering effort: three nines can be reached with good practices in one region; five nines generally requires multiple regions, automated everything and extremely careful change management.

3.2 Availability in series vs in parallel

A request usually passes through several components. How do their availabilities combine? Assume failures are independent (an important caveat — see 3.3).

In series (the request needs all of them): multiply.

A_series = A1 × A2 × … × An

In parallel (redundant copies; the request needs at least one): the system fails only if all copies fail.

A_parallel = 1 − (1 − A1) × (1 − A2) × … × (1 − An)
two copies of 99%:   1 − 0.01 × 0.01   = 1 − 0.0001  = 99.99%
three copies of 99%: 1 − 0.01^3        = 99.9999%
Series multiplies availabilities (down); redundancy in parallel multiplies unavailabilities (up). Always find the weakest serial link.

Let's verify the numbers. Series: 0.9999³ = 0.99970; × 0.995 = 0.99470; × 0.999 = 0.99370 → 99.37%, i.e. 0.63% × 8,766 h ≈ 55 hours/year. With three feed instances and a Redis replica: 0.99970 × 0.9999999 × 0.999999 ≈ 99.97% (~2.6 h/year). The remaining downtime now comes from the three single-instance edge components — so we make those redundant too (multiple DNS providers/anycast, LB pairs, many gateway instances). That is precisely why every layer in the Instagram diagram is drawn as a single box but deployed as many.

💡 Two quick rules (1) Adding a dependency in series can only lower availability — every synchronous call is a liability, which is one reason to move work to async queues. (2) A system can't be more available than its least available serial dependency — so a 99.99% target means every critical-path dependency must be (effectively) better than 99.99%.

3.3 The independence trap: correlated failures

The parallel formula assumes copies fail independently. In reality, failures are often correlated: all three replicas run the same buggy release; all sit in one data centre that loses power; all read the same bad config push; all depend on the same DNS or auth service. Three "independent" 99% replicas that share a deploy pipeline are not 99.9999% available. Defences: spread replicas across failure domains (racks, availability zones, regions), deploy gradually (canary one zone first), keep dependencies diverse where it matters, and design so that a bad change can be rolled back automatically.

4. Redundancy and single points of failure

A single point of failure (SPOF) is any component whose failure takes down the whole system (or a whole feature). Redundancy — having spare capacity or duplicate components — removes SPOFs.

4.1 Hunting SPOFs in a naive Instagram

4.2 How much redundancy?

  • N+1: enough capacity to lose any one unit (server, zone) and still serve peak load. With 3 zones, each zone must handle 50% of peak → you provision 150% of peak.
  • N+2: survive one planned outage (maintenance) plus one unplanned failure at the same time.
  • Data redundancy: replication factor 3 is the common default for databases and logs; object stores use replication or erasure coding (e.g. 10 data + 4 parity fragments) for durability at lower overhead (Object Storage).

5. Failover: active-passive vs active-active

Failover is switching traffic from a failed component to a healthy one. It needs three things: detection (health checks, heartbeats), a decision (who's the new primary — ideally via consensus to avoid two primaries) and redirection (update the LB, DNS or client routing).

Standby flavours: hot (running and in sync, takes over in seconds), warm (running but behind or under-provisioned, minutes), cold (restored from backups when needed, hours). The choice trades cost against RTO (recovery time objective: how long you may be down) and RPO (recovery point objective: how much recent data you may lose).

⚠️ Split brain and fencing If the network between a primary and its standby breaks, the standby may conclude the primary is dead and promote itself — while the primary is actually alive and still accepting writes. Now two primaries diverge. Systems prevent this with a consensus-based leader election (ZooKeeper/etcd, Raft) and fencing: each new leader gets a higher "epoch" number, and storage rejects writes carrying an old epoch. This is CAP in practice — see CAP & Consistency.

6. Reliability vs availability vs durability vs fault tolerance

These words are often used interchangeably, but interviewers notice when you distinguish them precisely.

PropertyQuestion it answersMeasured asInstagram example of a failureMain techniques
ReliabilityDoes the system do the right thing, consistently, over time?Error rate, MTBF, correctnessA like is recorded twice; a post appears for the wrong audienceTesting, idempotency, validation, careful rollouts
AvailabilityCan users use it right now?% uptime or % successful requestsFeed returns 503 for 10 minutesRedundancy, failover, load balancing, degradation
DurabilityOnce stored, will the data still exist later?Probability of data loss per object per year (e.g. 11 nines)A photo is permanently lost after a disk failureReplication, erasure coding, backups, checksums
Fault toleranceDoes it keep working when parts fail?Which failures it survives (node, zone, region)Losing one Cassandra node causes errorsRedundancy, quorums, retries, isolation (bulkheads)
ResilienceHow well does it absorb and recover from stress?Recovery time, degradation behaviourA traffic spike causes a cascading failureTimeouts, circuit breakers, load shedding (Resilience)

Some illuminating contrasts:

  • Available but unreliable: the feed always loads, but sometimes shows posts from blocked users. Up, but wrong.
  • Durable but unavailable: during a regional outage your photos are safe on disk but can't be viewed for an hour.
  • Available but not durable: a cache that always answers but loses everything on restart — fine for a cache, unacceptable for a database of record.
  • Fault tolerance is a means, availability is an end: you build fault tolerance (redundancy, failover) in order to achieve availability and durability targets.

A key design idea is graceful degradation: when part of the system fails, reduce functionality instead of failing entirely. If the ranking service is down, serve the timeline in chronological order; if like counts can't be fetched, hide them; if the CDN can't reach the origin, serve a slightly stale cached copy. Users experience "a bit worse" instead of "broken".

7. Performance

7.1 Latency vs throughput

  • Latency: time to complete one operation (ms). "How long did my feed take to load?"
  • Throughput: operations completed per unit time (requests/s, MB/s). "How many feeds can we serve per second?"
  • Bandwidth: the maximum possible throughput of a channel (e.g. a 10 Gbps link).

Analogy: a motorway. Latency is how long one car takes to drive from A to B; throughput is how many cars pass per hour. Adding lanes raises throughput without making any car faster; raising the speed limit lowers latency. They interact through queueing: as throughput approaches capacity, queues form and latency rises sharply (section 7.5). Some techniques trade one for the other — batching (e.g. Kafka producers batching messages, or fan-out workers writing timelines in bulk) raises throughput but adds a little latency to each item.

7.2 Percentiles: p50, p95, p99

Latency is a distribution, not a number. The pN (N-th percentile) is the value below which N% of measurements fall.

20 feed requests, sorted latencies (ms):
 42 45 47 48 50 51 53 55 56 58 60 62 65 70 75 80 95 120 250 1,900

mean = 3,282 / 20 ≈ 164 ms     ← dragged up by one 1.9 s outlier; describes nobody
p50  (median) ≈ 59 ms          ← the typical experience
p95           ≈ 250 ms         ← 1 in 20 requests is at least this slow
p99           ≈ 1,900 ms       ← the tail (with only 20 samples, p99 ≈ the max)
  • p50 shows typical performance; p95/p99 show the tail, which is what frequent users actually feel — someone loading 20 feed pages a day hits the p95 roughly once a day.
  • Never average percentiles across servers or time windows (the average of p99s is not the p99). Aggregate the underlying histograms instead (Observability).
  • Tail causes include garbage-collection pauses, cache misses, a slow disk, a noisy neighbour, retries, lock contention, and queueing at high utilisation.

7.3 Tail latency amplification under fan-out

Here is a subtle but crucial effect. When one user request fans out to many backend calls in parallel and must wait for all of them, the request is as slow as the slowest call. If each backend is "slow" (above its p99) 1% of the time, independently:

P(user request is slow) = 1 − P(all N calls are fast) = 1 − 0.99^N
Tail latency amplification: 1 − 0.99N. The rare becomes the common as fan-out grows.

Instagram example: rendering one feed page hydrates ~20 posts, each requiring metadata, counters, author info and "did I like it?" lookups spread over many cache shards — easily 20–100 parallel calls. With N = 20, 18% of feed requests experience some backend's p99. Flip it around: to keep the page p99 at a target, each backend must meet that target at the p99.95 level, because 0.991/20 ≈ 0.9995.

Mitigations (from Google's well-known paper The Tail at Scale and common practice):

  • Reduce fan-out: batch lookups (one multi-get per shard instead of one call per item), denormalise data so fewer services are touched.
  • Hedged requests: if a call hasn't returned by its p95, send a duplicate to another replica and take whichever answers first (costs a few % extra load).
  • Tight timeouts + partial results: render the feed without one post's like count rather than wait (graceful degradation).
  • Reduce variance at the source: avoid GC pauses, isolate noisy neighbours, keep utilisation moderate, use load-aware balancing.
  • Pre-compute: serve a pre-built timeline instead of assembling it from many sources per request — exactly what the Feed Cache does.

7.4 Little's law

Little's law is a simple, universally applicable relationship for any stable system (a server, a queue, a whole service):

L = λ × W
L = average number of requests in the system (concurrency / in-flight)
λ = average arrival rate (throughput, requests/s)
W = average time each request spends in the system (latency, s)

Uses:

  • Sizing concurrency: the feed tier at 350K req/s peak with 100 ms average latency has 350,000 × 0.1 = 35,000 requests in flight. If each server can work on 64 requests concurrently, you need at least 35,000 / 64 ≈ 550 servers — just for concurrency.
  • Connection pools: a service doing 20,000 DB queries/s at 5 ms each needs ~20,000 × 0.005 = 100 connections on average (plus headroom). Too small a pool → requests queue; too large → the DB drowns in connections.
  • Latency spikes eat capacity: if a dependency slows from 100 ms to 1 s, concurrency at the same throughput rises 10× — threads and connections run out and the slowdown cascades. This is why timeouts and circuit breakers are essential.
  • Queues: a Kafka consumer group with 2M messages of lag processing 50K messages/s means new events wait ~40 s (W = L / λ) — directly the "post visible to followers" delay.

7.5 Utilisation and queueing: why you need headroom

Queueing theory gives a sobering rule: as a server's utilisation ρ (busy fraction) approaches 100%, waiting time explodes. For the simplest model (M/M/1 — random arrivals, one server), average time in system is:

W = S / (1 − ρ)        S = service time when idle
ρ = 50%  → W = 2 S
ρ = 70%  → W ≈ 3.3 S
ρ = 80%  → W = 5 S
ρ = 90%  → W = 10 S
ρ = 95%  → W = 20 S
ρ = 99%  → W = 100 S

Real systems differ in detail, but the shape — a "hockey stick" — is universal. That's why capacity plans target ~60–70% peak utilisation, not 100%: the last 30% of "unused" capacity is what keeps the p99 sane and absorbs spikes and failovers (Estimation).

7.6 Bottleneck analysis

A system's throughput is limited by its bottleneck — the most constrained resource on the path. Speeding up anything else doesn't help. A systematic approach:

  1. Draw the request path (e.g. feed: LB → gateway → feed service → Redis → post cache → Cassandra on miss → ranking).
  2. For each stage, compare demand to capacity: requests/s vs per-node limit × nodes; bytes/s vs NIC/disk bandwidth; memory vs working set.
  3. Check resources with the USE method: for each resource (CPU, memory, disk, network, connection pools, locks) look at Utilisation, Saturation (queue length) and Errors.
  4. Find the latency budget hogs with distributed tracing: which span dominates the p99? (Observability)
  5. Fix the top bottleneck, then re-measure — the bottleneck moves. After caching the feed, ranking may become the slowest stage; after optimising ranking, the network to Redis may be.

Common bottlenecks in Instagram-like systems: a hot shard (a celebrity's posts or counters), the primary database for writes, cache-miss storms after a cache restart, fan-out workers lagging behind during a spike, and cross-region round trips. Amdahl's law is the reminder for parallelism: if 10% of the work is inherently serial, no amount of parallel workers can make it more than 10× faster.

8. Maintainability and operability

Most of a system's cost over its lifetime is not building it but running and changing it. Three facets (as framed in Martin Kleppmann's Designing Data-Intensive Applications):

🛠️ Operability

Easy for operators to keep healthy: good monitoring and alerts, automation, runbooks, safe deploys and rollbacks, predictable behaviour, no manual steps in failover.

🧩 Simplicity

Easy for new engineers to understand: clear service boundaries, good abstractions, no accidental complexity. Choose boring, proven technology unless there's a strong reason not to.

🔄 Evolvability

Easy to change: loosely coupled services, versioned APIs, schema evolution, feature flags, events that let new consumers be added without touching producers.

In the Instagram diagram, Kafka is a big maintainability win: when the company wants a new feature that reacts to posts (say, a "creator insights" dashboard), a team adds a new consumer — the Upload Service doesn't change. Splitting services by function (Y-axis) lets hundreds of engineers deploy independently. Public Instagram talks have long emphasised operational simplicity — "do the simple thing first" and use proven technology — which let a tiny early team run a fast-growing service.

11. Trade-offs & common pitfalls

✅ What these techniques buy

  • Horizontal scaling → near-unlimited capacity and redundancy
  • Redundancy + automatic failover → four nines and beyond
  • Replication/erasure coding → durability measured in many nines
  • Caches and pre-computation → low, predictable latency
  • Async queues → spike absorption, failure isolation

⚠️ What they cost

  • Distributed systems complexity: partial failures, consistency trade-offs
  • 2–3× hardware for redundancy and headroom
  • Replication lag → stale reads; failover → possible data loss (RPO)
  • Caches → invalidation bugs and miss storms
  • More moving parts to monitor and operate

Common pitfalls

  • "We'll scale vertically forever." Works until it suddenly doesn't — and the migration happens under pressure.
  • Hidden state in "stateless" services: local file uploads, in-memory sessions, local caches assumed to be authoritative.
  • Redundancy in the same failure domain: two replicas on the same rack, or a "backup" in the same region.
  • Assuming independent failures: correlated failures (bad deploys, config pushes) are the most common cause of big outages.
  • Untested failover: a standby that has never been promoted probably won't work when needed. Practise it (game days, chaos testing).
  • Reporting averages: the mean hides the tail; use p99 and p99.9.
  • Running hot: 90% utilisation looks efficient but makes latency explode and leaves no room for failover.
  • Ignoring fan-out: a page touching 100 services will be slow at the tail unless you mitigate.
  • Every extra nine everywhere: over-engineering low-value features wastes money; match SLOs to user impact.

13. Interview corner

What's the difference between vertical and horizontal scaling, and which would you use for Instagram?

Vertical scaling buys a bigger machine — simple, no code changes, but it has a hard ceiling, gets expensive near the top, and remains a single point of failure. Horizontal scaling adds more machines behind a load balancer — near-unlimited and redundant, but requires stateless services or partitioned data. For Instagram: horizontal everywhere — stateless services cloned behind LBs, Redis and Cassandra clusters, sharded PostgreSQL. Vertical scaling is still useful tactically, e.g. giving database primaries large machines to delay resharding.

Explain the scale cube with Instagram examples.

X-axis: clone — hundreds of identical Feed Service instances behind a load balancer; DB read replicas. Y-axis: split by function — separate Upload, Feed, Like & Comment, Follow, Search and DM services, each scaled and deployed independently. Z-axis: split by data — posts partitioned by user_id across Cassandra nodes; users across PostgreSQL shards. Each solves a different limit: X for stateless throughput, Y for organisational and functional scaling, Z for data size and write throughput.

A request goes through 5 components each with 99.9% availability. What's the end-to-end availability, and how do you improve it?

In series: 0.9995 ≈ 99.5% — about 44 hours of downtime a year, worse than any single component. Improve by (1) making each component redundant: two independent 99.9% copies in parallel give 1 − 0.001² = 99.9999%, so the chain becomes ≈ 99.9995%; (2) removing components from the synchronous path (move work to async queues); (3) graceful degradation so a failing non-critical dependency doesn't fail the request; (4) spreading replicas across failure domains so failures really are independent.

Active-passive or active-active for Instagram's user database?

Active-passive per shard: each PostgreSQL shard has one primary that accepts writes (so unique constraints like usernames remain simple and strongly consistent) and replicas that serve reads and act as hot standbys. Failover is automated with consensus-based leader election and fencing to avoid split brain; with synchronous or semi-synchronous replication to at least one standby, RPO can be ~0. Active-active writes would require conflict resolution for usernames — unacceptable. Stateless services, LBs and Cassandra, by contrast, run active-active.

Define reliability, availability, durability and fault tolerance, and give an Instagram failure example for each.

Reliability: doing the right thing consistently — failure: a like counted twice. Availability: being usable now — failure: the feed returns errors for 10 minutes. Durability: stored data survives — failure: a photo lost forever after disk failures. Fault tolerance: continuing to work despite component failures — failure: losing one Cassandra node causes write errors. Fault tolerance is the means; availability and durability are the goals.

Why do you care about p99 more than average latency, and what is tail latency amplification?

The average is skewed by outliers and hides what the slowest users experience; heavy users hit the tail daily. Amplification: when a request fans out to N backends in parallel and waits for all, it's as slow as the slowest. If each is slow 1% of the time, the request is slow with probability 1 − 0.99N: 18% at N = 20, 63% at N = 100. A feed page hydrating many posts is exactly this case. Mitigate with batching (fewer calls), hedged requests, timeouts with partial results, and pre-computed timelines.

Use Little's law to size something in Instagram.

Feed tier: λ = 350K req/s at peak, W = 100 ms → L = 35,000 concurrent requests. If a server handles 64 concurrent requests, we need ≥ ~550 servers for concurrency alone, before headroom. Or a DB pool: 20K queries/s × 5 ms = 100 connections. It also explains cascading failures: if a dependency's latency rises 10×, in-flight requests rise 10× at the same throughput, exhausting threads and pools — hence timeouts and circuit breakers.

How do you find the bottleneck in a slow feed endpoint?

Trace the path (LB → gateway → feed service → Redis timeline → post hydration → ranking) with distributed tracing and look at which spans dominate the p99. For each resource apply USE (utilisation, saturation, errors): CPU on feed hosts, Redis ops/s per shard (a hot shard?), cache hit ratio (miss storm?), connection-pool waits, GC pauses. Fix the top one, re-measure — the bottleneck moves. Typical culprits: N+1 calls during hydration (fix with multi-get), a hot Redis shard (replicate/split hot keys), or ranking-model latency (cache scores, cap candidates).

14. Check your understanding

Numeric: two independent load balancers, each 99.9% available, in active-active. Combined availability?

1 − (0.001 × 0.001) = 1 − 0.000001 = 99.9999% — assuming truly independent failures (different racks/zones, staggered deploys).

Numeric: how much downtime per month does 99.95% allow?

0.05% of ~43,830 minutes (average month) ≈ 21.9 minutes.

Numeric: MTBF = 500 hours, MTTR = 30 minutes. Availability? What if MTTR drops to 30 seconds?

500 / 500.5 ≈ 99.90%. With MTTR = 30 s (0.00833 h): 500 / 500.00833 ≈ 99.998%. Faster recovery is often the cheapest path to more nines.

Numeric: a page calls 50 backends in parallel; each has a 1% chance of being slow. What fraction of pages is slow?

1 − 0.9950 ≈ 1 − 0.605 = ~39.5%.

Scenario: your three Redis replicas are in the same availability zone. Is the cache highly available?

Only against single-node failures. A zone outage (power, network) takes out all three at once — a correlated failure. Spread replicas across zones (and ideally have the feed degrade gracefully if the cache tier is lost).

Scenario: a service runs at 92% CPU at peak and its p99 is erratic. Why, and what do you do?

Queueing: near full utilisation, waiting time grows like 1/(1 − ρ) — at 92% it's ~12× the service time and very sensitive to bursts. Add capacity (or cut per-request work) to bring peak utilisation to ~60–70%, and add load shedding/rate limiting to protect it from spikes.

Which property is violated: "Users' photos were all still on disk after the outage, but nobody could view them for 2 hours"?

Availability was violated; durability was preserved. The fix lies in redundancy and failover (e.g. serving from another region), not in more data copies.

Why must Instagram's app servers be stateless, and what's the one tier in the diagram that can't be fully stateless?

Statelessness lets the load balancer send any request anywhere, enables autoscaling, zero-downtime rolling deploys, and loss of an instance without data loss. The Direct Messaging WebSocket tier holds long-lived connections, so it's connection-stateful; it keeps all durable state (messages, presence) in external stores and uses a routing registry so any instance failure only drops connections, which clients re-establish.

🎯 Key takeaways
  • Scale out stateless services; scale data with replicas (reads), sharding (size/writes) and caches. The scale cube's X, Y, Z axes combine.
  • Availability: series multiplies (A1×A2…), parallel = 1 − Π(1 − Ai). Kill SPOFs, spread across failure domains, beware correlated failures; recover fast (MTTR).
  • Active-passive = simple writes, slower failover, split-brain risk; active-active = instant failover, harder writes.
  • Reliability ≠ availability ≠ durability; fault tolerance is how you get them. Degrade gracefully.
  • Measure p99; fan-out amplifies tails (1 − 0.99N); L = λW; keep utilisation ~60–70%; fix the real bottleneck, then re-measure.
  • Maintainability and cost are requirements too — every Instagram box exists to buy one of these properties.
